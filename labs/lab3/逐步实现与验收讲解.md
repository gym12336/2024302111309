### 5. 本轮先理解的名词

| 名词 | 通俗解释 |
|---|---|
| 物理内存 | 模拟机器实际拥有的RAM，类似仓库里真正存在的货架 |
| 物理页 | 内存分配的固定大小块，本实验一页4096字节，类似一整格货架 |
| 物理页分配器 | 记录哪些页空闲，并提供申请和归还服务的管理员 |
| 虚拟地址 | 程序看到的地址，类似各办公室内部自己的柜号 |
| 页表 | 虚拟柜号到实际货架位置的对照表，还规定能否读、写、执行 |
| SV39 | RISC-V的一种分页机制，用三级索引和页内偏移找到实际内存 |
| 映射 | 在页表中登记“这个虚拟页对应哪个物理页、允许怎样访问” |
| 配额 | 允许分配的资源上限，用来规定内存耗尽的边界 |
| 回滚 | 做到一半失败，把本次已经改变的部分撤销，恢复一致状态 |
| 保护页 | 故意不给用户访问的页区，本实验计划用未映射空洞发现栈越界 |
| 深拷贝 | 不只复制地址记录，还为子进程分配新物理页、复制实际数据 |
| OOM | Out Of Memory，内存不足；应返回错误并回滚，而不是把内核弄崩 |

例子：借10本书，只借到第6本时发现库存不足。如果这项申请约定“全部借到才算成功”，就要退回前6本，并恢复借阅记录。这里“书”像物理页，“借阅记录”像页表项，二者的回收责任都要明确，这就是Lab3重点考查的回滚一致性。

#### 用例A：访问用户栈下方保护页

1. 按最终装载布局，计算2页保护区的实际虚拟地址；不能拿任意小地址冒充保护页。
2. 父进程创建子进程，子进程对保护区中的地址做一次明确读或写。
3. 预期触发用户访存页错误；例如读缺页对应 `scause=13`，写缺页对应 `scause=15`。
4. 内核识别来自U态的非法访问，终止该子进程，给父进程可检查的非零退出状态。
5. 父进程 `wait` 回收后仍能输出，Shell还能运行hi，内核不能整体停机。

**验证重点：** 故障进程结束、父进程继续、现场和内存能够回收。官方badaccess写地址0主要检查代码页不可写，不能用它代替所有保护页测试。

#### 用例B：跨用户页边界拷贝

1. 通过 `sbrk` 申请足够空间，选取两个相邻且有效的用户虚拟页。
2. 从第一页末尾2字节开始放6字节 `ABCDEF`：第一页放AB，第二页放CDEF。
3. 调用 `write(1, address, 6)`，预期输出完整ABCDEF并返回6。
4. 确认拷贝函数跨到下一虚拟页后重新查表，不能假定两页对应物理内存也相邻。
5. 对应增加反向copyout检查，以及第二页无权限/未映射的失败检查；核对失败策略和两侧哨兵值，避免越界写。

**边界**是两块页之间的接缝。只检查开始地址就一路复制，类似只确认第一间房能进，就穿墙走进第二间房；跨页必须重新核对映射和权限。

### 2. 文件一：kernel/riscv.h，增加防重复包含保护

操作：将 `labs/lab3/gifts/kernel/riscv.h` 原样安装到 `kernel/riscv.h`，没有修改课程文件内部内容。

核心新增位于第9～10行及文件末尾：

```c
#ifndef RISCV_H
#define RISCV_H

// 原有CSR读写函数、页表类型与宏等内容

#endif // RISCV_H
```

这里代码块中的中间注释是省略说明，不是对原文件另作修改。

- `#ifndef RISCV_H`：如果本次预处理尚未定义RISCV_H，就继续读取内部内容。
- `#define RISCV_H`：做一个“本文件已经读过”的标记。
- `#endif`：结束这个条件范围。

**预处理**发生在C编译之前，处理include和宏等指令。**头文件**常用来提供多个源文件共享的类型、常量和函数声明；riscv.h中还包含内联函数定义。

例子：以后某个C文件直接include riscv.h，同时又include一个内部也包含riscv.h的头文件。没有保护，同一份函数定义可能被展开两遍，编译器会报重复定义；有保护，第二次就跳过内部内容。

注意：保护范围是每次源文件的预处理过程，不是“整个操作系统只能使用一次此头文件”，也不是用户运行时的一把锁。

**它怎样连接下一步：** 分配器需要PGSIZE、页对齐宏等；后面的vm代码和进程结构又需要页表类型。防重复包含保证这些文件组合起来仍可编译。

### 3. 文件二：kernel/trampoline.S，官方段属性与对齐修复

操作：将 `labs/lab3/gifts/kernel/trampoline.S` 原样覆盖 `kernel/trampoline.S`。核心变化在第22～23行：

```asm
.section trampsec, "ax"
.align 12
```

**段Section**是目标文件中同一类代码或数据的集合，链接器决定它最后放在哪里。这里的trampsec是跳板代码所在段。

- `a`：该段具有装载到运行内存的属性。
- `x`：该段包含可执行代码。
- 本RISC-V汇编中的 `.align 12`：将位置按 `2^12=4096` 字节对齐。

**对齐**就是让起始地址落在指定大小的整倍数边界。例如4096字节对齐相当于“从一整页的开头开始放跳板”，方便页表按整页映射。

这些以点开头的语句是汇编器的组织指令，不是CPU运行时每次执行的操作。不能把 `.align 12` 解释为运行时申请12页。

Lab2原本已经通过包装文件和链接脚本实现等效修复，所以这次不是“第一次修好能跑的跳板”，而是统一为Lab3官方支撑版本。uservec保存现场、userret恢复现场的主体逻辑保持课程版本。

**它怎样连接下一步：** 动态内核页表与用户页表仍须把同一份跳板代码映射到相同高虚拟地址。跳板先具有正确的物理装载和对齐，后面才有可映射的实际代码页。

### 5. 文件四：Makefile，让包含文件变化也会触发重编译

第32行新增：

```makefile
kernel/trampoline_link.o: kernel/trampoline.S kernel/riscv.h kernel/memlayout.h
```

冒号左边是需要生成的目标文件，右边是依赖。make发现右边文件更新，就重新生成左边目标。

**目标文件 `.o`**是单个源文件编译后的机器代码片段，最后由链接器组合成内核镜像。

为什么显式写这行？实际被编译的文件是trampoline_link.S，trampoline.S被它include。如果make不知道这层依赖，只改trampoline.S可能不会重编译包装目标，运行的仍是旧跳板。像改了教材内页，却仍拿上次打印的装订本来讲课。

**本步构建衔接：**

```text
kernel/trampoline.S、riscv.h、memlayout.h
    → 被trampoline_link.S包含或间接使用
    → 编译成kernel/trampoline_link.o
    → kernel/kernel.ld收集和定位跳板段
    → 链接出kernel/kernel
    → 启动页表把实际跳板页映射到TRAMPOLINE
    → uservec/userret执行用户与内核往返
```

### 2. 具体文件一：kernel/kalloc.h，先约定调用方式

新增文件：[kalloc.h](../../kernel/kalloc.h)。第7～12行定义：

```c
struct kalloc_stats {
  uint64 first_pa;
  uint64 limit_pa;
  uint64 total_pages;
  uint64 free_pages;
};
```

**结构体**把一组相关信息装在一起；这里是一次统计结果，不是物理页本身。

| 字段 | 意思 |
|---|---|
| first_pa | 管理范围的起点，包含这个地址对应的页 |
| limit_pa | 管理范围的终点，不包含这个地址对应的页 |
| total_pages | 分配器总共托管多少页 |
| free_pages | 当前有多少托管页尚未分配 |

第16～23行声明：

```c
int kinit(void);
int kalloc_get_stats(struct kalloc_stats *out);
void *kalloc(void);
int kfree(void *page);
```

**声明**告诉编译器“函数叫什么、接收什么、返回什么”，**定义**才是花括号里的实际做法。本步已经定义前两个函数；后两个只有声明，没有写假成功的空函数，也不允许现在就调用它们。

接口约定：

- kinit成功返回0；重复初始化或边界不合法返回-1。
- kalloc_get_stats把结果写到调用者提供的结构体，成功0；未初始化或out为空返回-1。
- 下一步kalloc返回一个已清零的完整物理页指针；耗尽或未初始化返回0。
- 下一步kfree成功返回0；不对齐、超范围、重复释放等非法请求返回-1。

**清零**表示返回的4096字节全为0，避免新使用者读到上一个使用者的数据。它在实际申请时做，本步kinit并没有把全部物理RAM逐页擦一遍。

### 3. 管理范围和配额公式：先避开内核，再扣预留页

文件：[kalloc.c](../../kernel/kalloc.c)，第36～42行：

```c
uint64 image_end = (uint64)kernel_end;
uint64 limit = PHYSTOP - (uint64)LAB3_MEMCAP_DELTA * PGSIZE;
uint64 first = PGROUNDUP(image_end);
```

实际代码还先检查image_end是否处于合理范围，避免在错误地址上计算并继续初始化。

公式为：

```text
first = 向上按4096对齐(kernel_end)
limit = PHYSTOP - 13 × 4096
可管理区间 = [first, limit)
total_pages = (limit - first) / 4096
```

`[first, limit)`是左闭右开区间，表示包含first，不包含limit。比如 `[100, 104)` 包含100、101、102、103，不包含104。

为什么不能直接从kernel_end开始？它可能落在一页中间。如果把这页交给别的模块，清零或写数据就可能擦到同页内核内容，因此必须整页向上对齐。

为什么不是128MB除4096再减13就完事？那样还把内核正在占用的页算进了可分配页。这里内核占用由first排除，13页配额由limit排除，剩下的才是分配器托管区。

当前PHYSTOP为 `0x88000000`，因此：

```text
limit = 0x87ff3000
预留区 = [0x87ff3000, 0x88000000)，共13页
最高可分配页的起始地址 = 0x87ff2000
```

first随链接后的内核大小变化，不能写死旧地址。位图本身属于内核静态存储，未来正式链接时也算在kernel_end之前，不会把登记册占的内存再分出去。

设计选择：配额通过预留最高端13页兑现；不是为每个进程各扣13页，也不是每申请一次都扣13页。后续页表页、程序页等只要从本分配器申请，都会占用同一池中的空闲页。

### 4. 为什么选择位图，而不是有序链表

**位图Bitmap**是用二进制的一位记录一个对象状态。这里一个bit对应一个物理页：1表示空闲，0表示不可分配或已分配。

128MiB物理RAM对应：

```text
页数 = 128 × 1024 × 1024 / 4096 = 32768
位图大小 = 32768 bit / 8 = 4096 byte
```

这里常说的128MB按工程实际的128×1024×1024字节计算。位图数组本身占4096字节，另有少量边界、计数和状态字段。

| 方案 | 如何满足降序 | 归还一页的代价 | 本轮选择 |
|---|---|---|---|
| 有序空闲链表 | 保持最高地址页在表头，分配摘表头 | 要找合适位置重新插入，最坏O(n) | 不选，批量回收可能退化为O(n²) |
| 位图 | 从高地址对应的空闲位向低地址找 | 按页号定位并更新一个bit，管理操作O(1) | 采用，并保存搜索位置 |

O(1)表示操作数量不随管理页数增长；O(n)表示最坏可能检查n项；O(n²)表示大批量操作的工作量可能按页数平方增长。释放时填充一页垃圾数据仍需要写4096字节，这是每页固定的额外工作，与有序链表扫描全部空闲页是不同成本。

位图不是所有方面都自动O(1)：分配仍要找空闲位。下一步会利用search_word避免每次从最高端重新扫过一大段已无空闲位的区域；不会把“位图”误说成“不用搜索”。

### 5. 位图怎样对应物理地址

第6～8行：

```c
#define RAM_PAGES ((PHYSTOP - KERNBASE) / PGSIZE)
#define BITS_PER_WORD 64UL
#define BITMAP_WORDS ((RAM_PAGES + BITS_PER_WORD - 1) / BITS_PER_WORD)
```

uint64有64个bit，因此每个数组元素可记录64页，整个数组需要512个uint64。

第47～49行：

```c
uint64 page = (pa - KERNBASE) / PGSIZE;
kmem.free_bitmap[page / BITS_PER_WORD] |=
    1UL << (page % BITS_PER_WORD);
```

- page是从RAM起点开始数的页号。
- page/64确定落在数组哪个元素。
- page%64确定这个元素中的哪一位。
- `1UL << bit`把一个1移动到所需位置。
- `|=`把该位设为1，同时保留其他位。

举例：页号65，65/64=1、65%64=1，因此在 `free_bitmap[1]` 的第1位记录它。bit编号从0开始，不是“页号65要访问数组第65项”。

### 6. kmem保存什么，为什么要单独记录搜索位置

第19～28行定义模块内部的kmem，包含：

- free_bitmap：所有RAM页的空闲登记位。
- first_pa、limit_pa：允许管理的边界。
- total_pages、free_pages：统计。
- search_word：下一步降序搜索从哪个位图元素开始。
- initialized：是否已经完成初始化。

static表示这个变量只供当前C文件内部直接使用，不是“每个进程都有一份”。内核中的分配器状态是一份，未来使用者要通过接口访问。

**降序语义**是每次选择当前空闲页中物理地址最高的一页，不只是第一次分配从高地址开始。下一步释放较高地址页后，也要调整搜索位置，确保它能被优先重新分配。

当前参数为1，代码通过_Static_assert明确要求本学生版本使用降序；没有声称本版本已经实现参数0的升序和参数2的中点策略。

### 7. kinit按什么顺序初始化

打开kalloc.c第31～59行，按下面顺序复述：

1. 检查initialized；重复调用返回-1。
2. 读取kernel_end、PHYSTOP和配额，计算完整托管区，检查边界。
3. 把整张位图置0，先默认所有页都不允许分配。
4. 仅遍历 `[first, limit)` 中每一完整页，将对应bit设1。
5. 保存边界，计算total_pages，并让free_pages初始等于total_pages。
6. 将search_word指到最高可分配页所在的位图元素；若没有可管理页，则用安全初值0。
7. 最后才置initialized=1，返回0。

先全关、再只开放合法区，可以确保内核区和预留区没有被误标记为空闲。

为什么防止重复初始化？设想以后页P已经交给页表模块使用，第二次kinit又把P标成空闲，另一个进程再申请到P，双方会互相覆盖。因此第二次初始化不能悄悄“清空重来”。

### 8. kalloc_get_stats做什么

第63～71行把当前边界与计数复制到调用者提供的结构体。out是**内核调用者提供的内核指针**，不是系统调用里的用户指针，这里不把它当用户地址做copyout。

目前仅初始化阶段使用，正式启动也未接入。后续申请/释放会修改计数，届时需要在单hart下保护位图和统计的一致性；当前代码不宣称已经支持多核并发。

本步保持：

```text
total_pages = free_pages
位图中所有1的数量 = free_pages
```

下一步有实际分配后，将维护：

```text
已分配页数 + free_pages = total_pages
```

Lab2的proc_shell_launch也从页对齐kernel_end之后安排固定进程槽。若现在同时启用新分配器并从同一区间发页，两套管理器可能都认为同一物理页归自己管理。
