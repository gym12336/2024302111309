## 第 1 步：先看懂目标，再确认原有内核能运行

### 1.1 这次实验究竟要让内核多做什么

Lab1 的内核能主动向屏幕输出文字，但还不能接受用户程序的请求或键盘输入。Lab2 最终希望看到 `sh>` 提示符：Shell 是一个用户程序，能读取键盘输入，再请求内核运行 `hi` 等程序。PDF 把工作分成四段：先修通用户态与内核态的往返（阶段一），再处理系统调用（阶段二），再接通键盘中断和输入缓冲（阶段三），最后装载 Shell（阶段四）。前一段是后一段的基础。

先记住三个 CPU 权限级别：**M 态**负责最早期机器设置；**S 态**是内核运行的监督权限；**U 态**是普通用户程序权限。它们是**同一颗 CPU 的三种工作权限**，不是三台机器。用户程序不能直接随意修改内核数据，所以需要按规定入口请求服务。

PDF 要求写代码前先画两条目标路径。第一条是 `write` 系统调用：

```text
用户程序（U 态）准备参数 → ecall → 跳板保存寄存器、换到内核栈
→ 内核 usertrap 判断原因 → syscall 找到 write 并输出
→ 内核把返回值放到 a0，准备返回地址 → 跳板恢复寄存器 → sret → 用户程序继续
```

第二条是键盘输入中断：

```text
键盘字符 → UART 串口设备 → PLIC 中断控制器 → CPU 进入内核
→ 内核从 UART 取走字符 → 放入输入缓冲区 → Shell 的 read 取走字符
```

把第一条路径再展开，方便以后对照代码逐段检查：

```text
U 态：用户程序把 write 的调用号放入 a7，参数放入 a0～a2，然后执行 ecall
  ↓ CPU 记录原因和返回位置，按委托设置跳到 stvec 指定的 S 态入口
S 态跳板 uservec：先暂存 a0，再把用户寄存器保存到 trapframe
  ↓ 从 trapframe 取出内核栈顶、内核页表和 C 入口，切换运行环境
S 态 C 函数 usertrap：识别 ecall，将返回位置从 ecall 推进到下一条指令
  ↓ syscall 根据 a7 分发到 write，把结果放入 trapframe 中的 a0
S 态 usertrapret / userret：准备返回环境，从 trapframe 恢复用户寄存器
  ↓ sret
U 态：用户程序从 a0 得到 write 的返回值，继续执行
```

再把第二条路径展开。它与 `ecall` 的最大区别是：输入由外部设备先发起，用户程序不需要先执行一条请求指令。

```text
键盘字符到达 UART 接收寄存器
  ↓ UART 打开接收中断后通知 PLIC；PLIC 再把中断送到 CPU
CPU 进入 S 态中断入口：保存被打断程序的现场
  ↓ 中断分发确认是 UART，读取字符并放进环形输入缓冲区
  ↓ 回显字符，告诉 PLIC 本次中断处理完毕，恢复被打断的执行位置
Shell 调用 read：从缓冲区取字符；若还没有字符，则按本阶段等待方案继续等
```

**系统调用**是用户程序主动发起的请求；**中断**通常是外部设备通知 CPU 有事要处理。`UART` 是这里模拟的串口输入输出设备；`PLIC` 负责把设备的中断送到 CPU。**缓冲区**是暂存输入字符的内存：键盘输入与程序读取不会总在同一时刻发生，需要先存起来。这里画的是 PDF 要求的目标路径，尚未发生在当前内核中；同样的设计图还存档在 [设计笔记](设计笔记.md)。

### 1.2 `ecall` 做了什么，为什么要保存寄存器

在 `write(1, "hi", 2)` 中，用户侧桩代码先把“我要调用哪个服务”放进 `a7`，把参数放进 `a0`、`a1`、`a2`，再执行 `ecall`。**寄存器**是 CPU 内部暂存数值的小空间。`ecall` 本身不打印 `hi`，它只是触发一次进入处理程序的异常。按本实验的委托设置，从 U 态发出的请求会进入 S 态；CPU 记录原因和当前指令地址，并跳到预设的入口。

权限切换不会换一套普通寄存器。内核也要用 `a0`、`sp`、`t0` 等寄存器，如果直接覆盖，用户程序返回后原来的计算结果就丢了。**trapframe（现场页）**是内存中保存用户寄存器快照的地方。`sp` 是栈指针；刚进入内核时它仍指向用户栈，跳板先保存它，再换成内核栈。系统调用返回时，大多数寄存器恢复原值；`a0` 则由内核有意改成返回值。

`sepc` 是 CPU 记录的陷入位置。对 U 态 `ecall` 而言，它指向 `ecall` 指令本身；这条指令长 4 字节，因此处理成功后需要让返回位置前进 4 字节，避免回去又执行同一条 `ecall`。设备中断的返回位置不能照搬这个“加 4”规则。`sret` 是从 S 态返回的指令，它按事先准备好的状态返回 U 态和目标位置。

### 1.3 为什么先做 Lab1 基线测试

“基线”是后续改动前，已知可以工作的状态。先在当前项目目录执行 `make clean && make`，再用 QEMU 启动旧内核并与 `expect_banner.txt` 逐字节比较。两份输出均为 446 字节，`cmp` 结果为相同，异常日志为空。这证明**原有启动和输出当时正常**，后续若黑屏，就能先检查最近改动。它不能证明任何 Lab2 功能通过。

动手前准备的自测包括：非法调用号返回 `-1`；缓冲区边界和空缓冲区读取；超长输入后内核仍正常；以及 Lab1 Banner 回归。这些测试将在相关功能实现后才执行，不能把“写了测试计划”当作“测试通过”。

## 第 2 步：把课程增量包接入工程

### 2.1 增量包里有什么，为什么先合并

PDF 说明有赠送的跳板、用户程序与构建支持。`gifts/kernel/trampoline.S` 是汇编协议的另一半，不能随意改；`gifts/user/sh.c`、`hi.c`、`spin.c` 是将来要运行的用户程序；`gifts/kernel/syscall.h` 给出调用号；`Makefile.upgrade` 给出构建规则。若不先核对这些接口，内核侧自行假定寄存器偏移或调用号，很容易和赠送程序不一致。

我们保留 `gifts/` 原件，再把它们复制到工程对应位置。通过哈希检查，18 份副本与原件内容一致。**哈希**可以理解为文件内容的校验指纹：相同的 SHA-256 值在这里用于确认复制时没有改变文件字节。

### 2.2 `Makefile` 到底做了什么

`Makefile` 是给构建工具 `make` 的操作说明。它决定先把每个 `.c`、`.S` 文件编成 `.o` **目标文件**，再把目标文件链接成内核。Lab2 增加了 `kernel/userimg.o`，并通过 `include Makefile.upgrade` 引入课程赠送的用户程序构建规则。这里的 `include` 是把另一个规则文件读进来，不是 CPU 运行时的操作。

用户程序先被编译为 `sh.bin`、`hi.bin`、`spin.bin` 等**平铺二进制文件**：里面是程序的原始字节。课程构建规则再生成 `kernel/userimg.S`，把这些字节放进内核镜像，并生成 `_uprog_table`。这张表记录“哪个名字的程序，其字节从哪里开始、到哪里结束”。当前没有磁盘文件系统，因此它暂时充当查找内嵌程序的目录。

### 2.3 本步验证到了哪里

`make` 成功生成三个用户程序，并在内核符号表中看到 `_uprog_table` 和三个程序起点；QEMU 再次输出与 Lab1 期望文件完全相同的 446 字节。**符号表**是镜像中的名称与地址清单，能证明名字被链接进来了。此时只证明程序**在内核镜像里**，还没证明内核能够装载它、进入 U 态并运行它。我们按增量包要求建立了本地 `lab2-start` 标签，作为此轮工作的起点。

## 第 3 步：让跳板能装载，并让高地址能访问

这一小步属于 PDF 的**阶段一：陷入处理框架**的基础准备。顺序是：CPU 看到什么地址 → 为什么需要跳板 → 链接器怎样放置它 → 页表怎样找到它 → 验收证据能证明什么。

对应代码可以随讲解逐个打开：[跳板包装](../../kernel/trampoline_link.S)、[链接脚本](../../kernel/kernel.ld)、[启动页表](../../kernel/boot_vm.c)、[目前的陷入诊断入口](../../kernel/trap.c)。

### 3.1 CPU 执行代码时需要地址

CPU 用 **PC（程序计数器）**保存下一条要执行的指令地址。代码和数据最终都在硬件内存中；它们在硬件内存中的位置叫**物理地址**。在 QEMU 的 `virt` 机器上，本项目内核所在的 RAM 从 `0x80000000` 开始。这里的十六进制前缀 `0x` 只是书写地址的方式，并不是另一种内存。

程序也可以使用**虚拟地址**。CPU 此时需要查一张地址换算表，才知道对应哪块物理内存。这张表叫**页表**。例如本步把虚拟地址 `0x3ffffff000` 指向物理地址 `0x80001000`：数字不同，实际访问的是同一页代码。一个物理页可以被多个虚拟地址指向，这叫**别名映射**。

地址的最小映射单位通常是**页**。本步细粒度页为 4 KiB，即 4096 字节；一个地址可分成“页号”和“页内偏移”。映射只替换页号，页内偏移保持不变。所以如果页首 `0x3ffffff000` 指向 `0x80001000`，那么虚拟地址 `0x3ffffff09c` 就指向物理地址 `0x8000109c`。

### 3.2 Lab2 为什么需要跳板

后续用户程序运行在 **U 态**（用户权限），内核运行在 **S 态**（监督权限）；启动时还经过权限更高的 **M 态**。这些是 CPU 的权限级别，不是三个独立程序。系统调用 `ecall` 发生时，CPU 将进入 S 态，但不会自动把全部普通寄存器保存好，也不会自动换成内核栈。保存寄存器、换栈、调用内核处理函数的汇编代码就是**跳板**（`trampoline.S`）。

将来用户程序和内核会使用不同的页表。跳板在换页表的那一刻仍要继续执行，因此两套页表都需要在同一个虚拟地址 `TRAMPOLINE` 找到同一页跳板代码。`TRAPFRAME` 是紧邻其下的一页虚拟地址，跳板把用户寄存器保存到那里的内存。`TRAPFRAME` 不等于寄存器本身；它是一块供汇编读写寄存器快照的 RAM。

```text
CPU 使用的虚拟地址                 页表换算             实际物理内存
TRAMPOLINE  0x3ffffff000   ──────────────────>   0x80001000 的跳板代码页
TRAPFRAME   0x3fffffe000   ──────────────────>   boot_trapframe 暂存页
```

这里还有一个重要区别：**代码放在哪里**与**CPU 用什么地址访问它**不是同一问题。链接器负责前者，页表负责后者；本步必须两边都处理。

### 3.3 链接器怎样把赠送汇编放入内核

这一段只解决一个问题：**跳板指令怎样成为内核镜像中真正可运行的代码？** 可以分成三步看：

```text
trampoline.S（人写的汇编源文件）
    ↓ 编译
trampoline_link.o（目标文件，尚未决定所有最终地址）
    ↓ 与其他目标文件链接
kernel/kernel（QEMU 装载的完整内核镜像）
```

目标文件 `.o` 像有许多分格的箱子：某格放代码，某格放数据。**section（节）**就是一个分格。赠送的 `trampoline.S` 用 `.section trampsec` 把跳板指令放进名叫 `trampsec` 的格子，但没有说明这个格子应在运行时分配内存、允许执行。原先的链接探针看到 `uservec=0x0`、类型 `N`；对本实验来说，这不是内核 RAM 中可执行的入口。

自有的 `trampoline_link.S` 先声明 `.section trampsec,"ax"`，再通过 `#include "trampoline.S"` 把赠送源码接进来。`a` 表示运行时给这一节分配内存，`x` 表示其中可以放要执行的指令。**赠送文件本身保持原样。**

接着由**链接器**读取 `kernel/kernel.ld` 决定“把这格放在哪”。脚本将其起点移到下一个 4096 字节整数倍，再安放 `trampsec`，并检查内容没有超过一页。因此两处标签的最终位置是：

```text
0x80001000  trampoline / uservec：用户进入内核的入口
     ……     保存寄存器等指令
0x8000109c  userret：内核返回用户的入口
```

**标签**是给指令位置起的名字。`userret` 距这页开头 `0x9c` 字节，所以它的地址是 `0x80001000 + 0x9c`；两处标签属于同一页。页首必须对齐，是为了下一步能把这一整页准确映射到固定虚拟地址 `TRAMPOLINE`。简记：`trampoline_link.S` 说明“这格是可执行代码”，`kernel.ld` 决定“这格放在 `0x80001000`”，页表随后负责“虚拟地址怎样找到它”。

### 3.4 `boot_vm.c` 每组操作在做什么

#### 3.4.1 先准备“地址查询表”和“现场存放处”

假设 CPU 要访问虚拟地址 `TRAPFRAME`。它需要一张查询表回答：“这个虚拟地址对应 RAM 的哪一页？”`boot_vm.c` 中的 `root` 就是查询起点。Sv39 采用**三级页表**：若第一张表没有直接给出最终物理页，就按记录找到第二张表，再找到第三张表。`top_l1`、`top_l0` 是这条查询链上后两张表。

为什么每张表是 `uint64 表名[512]`？一个 `uint64` 是 8 字节，`512 × 8 = 4096` 字节，恰好一页。数组中的一格叫**页表项 PTE**。`aligned(PGSIZE)` 要求这一页的起点能被 4096 整除，以便 CPU 按硬件格式找到它。

`boot_trapframe` 虽然也是 4096 字节、同样对齐，却**不是查询表**。它是映射成功后真正用来存放寄存器现场的 RAM。当前只有一页启动暂存空间；以后每个进程需要自己的现场空间。

`PX(2, 地址)`、`PX(1, 地址)`、`PX(0, 地址)` 分别从虚拟地址取出三级查询所需的数组下标。可以把虚拟地址想成写着“三层目录编号＋页内位置”的纸条：前面几个编号指导逐级查表，页内位置告诉 CPU 到最终那一页的哪个字节。

#### 3.4.2 为什么先给老地址做“原样换算”

开页表以前，Lab1 的内核代码位于 `0x80000000` 一带，UART 串口位于 `0x10000000` 一带。开启页表后，CPU 会把这些数值当成虚拟地址查表。如果表里没有它们，CPU 连下一条内核指令或串口寄存器都可能找不到，表现为无法继续运行或没有输出。

所以代码先加入两条大范围规则：

```text
虚拟地址 0x00000000～0x3fffffff → 数值相同的物理地址（包含 UART）
虚拟地址 0x80000000～0xbfffffff → 数值相同的物理地址（包含内核）
```

这叫**恒等映射**：输入什么地址，就换算成同数值的物理地址。`root[PX(2, UART0)]` 实际是 `root[0]`，`root[PX(2, KERNBASE)]` 实际是 `root[2]`。每条规则覆盖 1 GiB，叫**大页映射**。范围很宽，是为了先保证已有内核正常启动；后续为用户进程建立的页表需要更精细的范围和权限。

#### 3.4.3 两个高地址是怎样逐级找到物理页的

高地址需要精确到 4 KiB，不能用上一段覆盖 1 GiB 的粗规则。这里走完整的三级查询：

```text
root[255] → top_l1[511] → top_l0[511] → 0x80001000 跳板代码页
                            top_l0[510] → boot_trapframe 现场页
```

方括号里的数是数组下标，来自虚拟地址的不同部分。两条路线共享前两张表，最后才分开。于是 `TRAMPOLINE=0x3ffffff000` 找到跳板，紧邻的 `TRAPFRAME=0x3fffffe000` 找到现场页。

页表项 PTE 里除了“指向哪里”，还写着“允许做什么”。`PTE_V` 表示此项有效；`PTE_R` 是可读，`PTE_W` 是可写，`PTE_X` 是可执行。跳板页设为 **读＋执行**，因为 CPU 要读取并执行指令；现场页设为 **读＋写**，因为要保存和恢复寄存器。两页都没有 `PTE_U`，所以 U 态用户程序不能直接访问；跳板在 S 态可以访问。`PTE_A`、`PTE_D` 是访问和写入状态位，本步预先设置，避免它们影响这个最小映射实验。

#### 3.4.4 表填好后，怎样告诉 CPU 开始使用

此前 `satp=0`，S 态按地址数值直接访问，没有启用 Sv39 换算。`satp` 是 CPU 的**页表控制寄存器**。代码执行 `w_satp(MAKE_SATP(root))`，就是告诉 CPU：“从现在起用 Sv39，从 `root` 开始查表。”因此 `root` 自己必须放在 CPU 能找到的物理内存中。

CPU 可能缓存旧的地址换算结果；这个缓存叫 **TLB**。`sfence.vma` 让旧结果失效，以便后续访问按新表查询。你可以先把它理解为“换新目录之后，清掉手里旧的地址便签”。

最后，代码**实际走一遍两条新路线**：通过 `TRAMPOLINE` 读取指令，与 `0x80001000` 的内容比对；通过 `TRAPFRAME` 写入 `LAB2` 标记，再从 `boot_trapframe` 读回。若两边指向同一物理页，值应一致。检查完成后清掉标记，避免它成为后续现场里的垃圾数据。

### 3.5 这次验收能证明什么

验收分两层。第一层检查**内核文件里的摆放结果**：`nm` 是查看符号地址的工具，它显示 `uservec=0x80001000`，类型 `T` 表示代码符号；`readelf` 是查看内核文件结构的工具，它显示 `.trampsec` 具有 `AX` 属性。它们回答“链接器有没有把跳板放到合适的位置”，但不能单独证明 CPU 运行时能访问高地址。

第二层检查**QEMU 中的运行结果**：启动代码读写了两个高地址，并成功继续打印 Lab1 Banner。`cmp` 逐字节比较真实输出和期望文件，结果相同，两个文件均为 446 字节；异常日志为 0 字节。这说明这次开启页表后，两个新映射和原来的内核、UART 路径都能完成本次启动测试。

测试还没有让用户程序执行 `ecall`。因此它尚未验证“跳板保存所有寄存器 → 内核处理系统调用 → 跳板恢复寄存器”这条往返路。当前 `kernel/trap.c` 只有意外陷入时打印信息并停住的入口。后续会先把保存现场的 C 结构按赠送汇编的偏移定义好，再逐段接通往返。

## 已问过的概念：集中复习

### RAM 和 ROM 有什么区别？

**RAM** 是运行时通常可以读写的内存，断电后内容通常消失。本项目的内核代码、变量、栈和页表位于 QEMU 模拟的 RAM，起点是 `0x80000000`。**ROM** 在正常运行时主要供读取，常保存启动代码；本机的 QEMU 启动 ROM 位于 `0x1000` 附近，CPU 先执行它，再进入我们的内核。实际设备可能使用可更新的闪存保存固件，但在这个实验里先按“启动代码在 ROM，运行中的可修改数据在 RAM”理解。**虚拟地址**不是第三种内存，它只是经页表换算后访问 RAM 或设备的地址。

### `ecall` 是“执行 write”的指令吗？

不是。`ecall` 只是让 CPU 转去处理一个同步请求。用户程序在执行前先把调用号和参数放进规定的寄存器；进入内核后，内核才读取这些值并判断要执行 `write`、`getpid` 还是别的服务。若缺少陷入入口和内核分发代码，单独一条 `ecall` 不会替我们完成打印。

### 切换到 S 态后为什么还要保存寄存器？

U 态和 S 态使用同一颗 CPU 的同一组普通寄存器，权限变化不会自动复制寄存器。假设用户程序的 `t0` 留有计算结果，内核处理请求时也把 `t0` 当临时变量，原值就会被覆盖。跳板先把它记录到 trapframe，处理完再恢复。`sp` 更关键：刚进入内核时它还是用户栈指针，必须先记住，才能换成内核栈；回去时还要恢复用户栈。系统调用返回值所在的 `a0` 是有意修改的例外。

### 链接器和页表为什么都要处理跳板？

这是两个先后问题：**链接器**决定指令实际放在内核镜像的哪里，本步结果为 `0x80001000`；**页表**决定 CPU 使用虚拟地址 `TRAMPOLINE=0x3ffffff000` 时怎样找到那页指令。只做前者，高虚拟地址仍找不到代码；只做后者，若镜像里根本没装载可执行跳板，也没有正确代码可找。

## 第 4 步：给保存寄存器的内存定义统一布局

本步对应 PDF“阶段一：陷入处理框架”中的 **trapframe 定义**。代码在 [kernel/trapframe.h](../../kernel/trapframe.h)，检查工具在 [tools/check_trapframe.py](../../tools/check_trapframe.py)。本步先确定各项数据放在哪个位置；实际进入用户态和陷入返回要继续逐步实现。

### 4.1 为什么一页 RAM 还需要一个 C 结构体

第 3 步把 `TRAPFRAME` 虚拟地址映射到真实 RAM，解决了“能找到这块内存”。但一页 RAM 只有连续的字节，硬件不会在上面写出“这是 a0、那是 sp”。汇编和 C 必须事先约定每个值占多大、从哪里开始。

**结构体 `struct`** 是 C 中把多项数据按一个布局组织起来的类型。**字段**是其中某一项数据的名字。声明 `struct trapframe` 相当于画好这块内存的格子图；声明一个类型本身不会另外分配一页 RAM，也不会自动把寄存器保存进去。实际写入动作仍由赠送汇编的 `sd` 完成。

例如把现场起点写成 `B`，汇编 `sd ra, 40(a0)` 的意思是：把 CPU 的 `ra` 寄存器写到 `B + 40` 开始的 8 个字节，前提是此时 `a0=B`。`ra` 保存普通函数调用的返回地址；它与 `sepc` 保存的陷入返回位置是不同信息。C 以后通过 `tf->ra` 读取的也必须是 `B + 40`。

```text
现场起点 B
  B +   0 ～   7：kernel_satp
  B +   8 ～  15：kernel_sp
  B +  16 ～  23：kernel_trap
  B +  24 ～  31：epc
  B +  32 ～  39：kernel_hartid
  B +  40 ～  47：用户 ra
  B +  48 ～  55：用户 sp
             ……
  B + 112 ～ 119：用户 a0
  B + 168 ～ 175：用户 a7
  B + 280 ～ 287：用户 t6
```

这里的 **偏移**就是“距离起点多少字节”，不是数组的第几项。如果 C 把 `ra` 放在 `B+48`，汇编却写在 `B+40`，那么 C 读到的就是别的寄存器，返回时也会恢复错值。这是 PDF 特别要求逐项对齐的原因。

### 4.2 为什么所有字段用 `uint64`

`uint64` 在本项目中是 64 位无符号整数，大小为 8 字节。我们运行的是 64 位 RISC-V，普通寄存器保存的是 64 位内容；汇编 `sd` 存 8 字节，`ld` 取 8 字节。因此每个格子都用 8 字节来容纳地址或寄存器内容。

例如前面已经占了五个格子，`ra` 就从 `5 × 8 = 40` 字节开始。不能把某一项随意改成通常占 4 字节的 `int`，也不能交换顺序。编译器还可能按对齐规则在结构体中插入空隙，叫 **填充**；因此本步检查编译器最终算出的实际偏移，不能只相信手写注释。

### 4.3 最前面五项为什么不是普通用户寄存器

刚进入跳板时，CPU 已进入 S 态，但仍使用用户的栈和页表。跳板需要提前找到“内核栈在哪里、内核入口在哪里”等信息，才能安全进入内核 C 函数。因此现场前面预留了五项运行信息：

| 字段 | 偏移（字节） | 作用 | 后续谁负责准备 |
|---|---:|---|---|
| `kernel_satp` | 0 | 内核页表的控制值，汇编会写入 `satp` | 返回用户态前的内核准备代码 |
| `kernel_sp` | 8 | 下次进入内核时使用的内核栈顶 | 返回用户态前的内核准备代码 |
| `kernel_trap` | 16 | 内核 C 函数 `usertrap()` 的入口地址 | 返回用户态前的内核准备代码 |
| `epc` | 24 | 用户接下来要执行的指令地址 | C 保存 `sepc`，处理后再准备返回位置 |
| `kernel_hartid` | 32 | 当前硬件线程的编号，供跳板设置内核的 `tp` | 返回用户态前的内核准备代码 |

`kernel_satp` 不是只有页表指针，还包含页表模式等控制位，不能把原始指针直接当作整个 `satp` 值。**hart** 是 CPU 的硬件线程；目前只启动 hart0。`kernel_sp` 与后面偏移 48 的 `sp` 也不同：前者是内核使用的栈顶，后者是暂停的用户栈指针。

`epc` 不由赠送跳板的 `sd` 自动保存。CPU 在陷入时先记录 `sepc`，后续 `usertrap()` 的 C 代码把它复制到 `tf->epc`；返回准备代码再把要执行的位置写回 `sepc`。本步只定义这个位置，尚未实现这组保存和返回动作。

### 4.4 后面 31 个字段分别保存什么

RISC-V 有 32 个普通整数寄存器，其中 `x0` 永远读出 0，写入也不会改变它，所以不用保存。其他 31 个都需要在现场中有位置。表里的职责是普通函数调用时的约定；发生陷入时仍要把用户原值完整保存。

| 字段 | 偏移（字节） | 常见职责 |
|---|---|---|
| `ra` | 40 | 函数调用的返回地址 |
| `sp` | 48 | 用户栈指针 |
| `gp` | 56 | 全局数据访问所用的指针 |
| `tp` | 64 | 用户程序的线程指针；不能假定它本来就等于内核 hart 编号 |
| `t0/t1/t2` | 72 / 80 / 88 | 暂存计算中间结果，普通函数调用可改写它们 |
| `s0/s1` | 96 / 104 | 按普通调用约定需要被调用者保存的寄存器；`s0` 也可能用作帧指针 |
| `a0/a1/a2/a3/a4/a5/a6/a7` | 112 / 120 / 128 / 136 / 144 / 152 / 160 / 168 | 参数寄存器；本实验用 `a7` 传调用号，用 `a0` 返回结果 |
| `s2/s3/s4/s5/s6/s7/s8/s9/s10/s11` | 176 / 184 / 192 / 200 / 208 / 216 / 224 / 232 / 240 / 248 | 其余按普通调用约定需保存的寄存器 |
| `t3/t4/t5/t6` | 256 / 264 / 272 / 280 | 其余临时寄存器 |

**帧指针**是方便定位一次函数调用中局部数据的参考位置。你现在先记住它也是用户现场的一部分，不需要立刻掌握编译器如何使用它。系统调用还没有进入普通内核函数时，中断也可能在任意指令处发生，所以不能依据“这个寄存器普通函数会保存”就省略现场中的格子。

五个头部字段加 31 个寄存器字段，共 36 个，实际结构大小为 `36 × 8 = 288` 字节。第 3 步映射的一页仍然是 4096 字节；**映射的单位是一页，字段布局只用其中前 288 字节**。这些数字描述不同层面的大小。

### 4.5 为什么保存 `a0` 的汇编看起来特别绕

以 `write(1, "hi", 2)` 为例，刚陷入时用户 `a0=1`。但跳板又需要一个寄存器保存现场的起点，于是暂时借用 `a0`。先看真实的三组动作：

```asm
csrw sscratch, a0     # 先把用户 a0=1 暂存到 CPU 的 sscratch 控制寄存器
li a0, TRAPFRAME      # 此后 a0 是现场起点 B，不再是用户参数 1
                      # ……先保存包括用户 t0 在内的其他寄存器……
csrr t0, sscratch     # 此时可以借 t0 取回用户 a0=1
sd t0, 112(a0)       # 写入现场的 a0 格子，地址 B+112
```

`csrw` 是写控制寄存器，`csrr` 是读控制寄存器；`li` 把常量放入普通寄存器。这里 `sscratch` 是 CPU 的暂存控制寄存器，`tf->a0` 才是 RAM 中最终保存用户 `a0` 的格子。用户原来的 `t0` 已先存到 `B+72`，所以临时借用它不会丢失现场。

返回时汇编最后执行 `ld a0, 112(a0)`，先用右边的 `a0=B` 算出地址，再把保存的值装入左边的 `a0`。为什么最后才恢复它？因为之前恢复其他寄存器时还要不断使用 `a0` 作为现场起点。等其他内容取完，才可以放弃这个起点。日后系统调用分发若把 `tf->a0` 改成返回值，这最后一条就会把返回值交还用户程序。

### 4.6 怎样让错误布局在编译时就被发现

头文件对每个字段使用 **编译期断言 `_Static_assert`**：例如检查 `ra` 的实际偏移必须是 40，`a0` 必须是 112，总大小必须是 288。断言是在编译时检查的条件，不会变成内核运行时的一次函数调用。条件不成立，编译器立即停止，并说明哪个字段位置错了。本项目 GCC 在 `gnu99` 模式下支持这种检查。

此外，`tools/check_trapframe.py` 直接读取赠送汇编的保存与恢复偏移，生成检查代码，再让 RISC-V 编译器计算 C 布局。这避免只对着头文件注释自我核对。脚本还只在临时副本中交换 `a0/a1`，确认编译器确实拒绝错误布局；项目源文件不会被交换。`Makefile` 增加 `trap.o` 对该头文件的依赖，保证以后改字段时重新编译检查。

在 WSL 项目目录执行：

```bash
python3 tools/check_trapframe.py
make
```

本步实测输出：

```text
PASS: 31 register save/restore offsets match the compiled C layout
PASS: 36 fields, 288 bytes; a0=112, a7=168, sp=48, epc=24
PASS: swapping a0/a1 in a temporary header is rejected by the compiler
```

内核编译和链接成功。这证明 **C 字段位置与赠送汇编约定一致，并且布局错误能被拦住**。本步没有执行新的用户态往返测试，不能据此声称寄存器已经在实际 `ecall` 中完整保存恢复。

### 4.7 验收时怎样解释这一小步

可以这样回答：“汇编只认识现场起点和字节偏移，C 认识字段名。我用 `uint64` 按协议定义 36 个字段，使 `tf->ra` 与 `sd ra,40(a0)` 指向同一个位置；前五项是进入内核需要的环境信息，后 31 项保存除 x0 之外的用户寄存器。检查脚本从原汇编取偏移，由编译器逐项核对，并确认交换 a0/a1 会导致编译失败。现在只完成现场布局，下一步继续准备内核栈和返回环境。”

## 第 5 步：提前准备进入内核所需的环境

### 5.1 为什么有了 trapframe，还要填写内核信息

第 4 步定义了保存现场的格式，相当于准备了一张带栏目名称的表格。但表格中的“内核栈在哪、内核页表是什么、进入哪个处理函数”还没有内容。赠送跳板不负责替我们创建这些资源，因此本步要先准备资源，再把地址填到对应栏目。

假设用户程序以后执行 `ecall`。CPU 切到 S 态并跳到陷入入口时，**普通寄存器不会自动换成内核的值**，其中 `sp` 仍指向用户栈。跳板保存用户寄存器之后，需要给 `sp` 换一个安全的内核栈地址，然后切到内核页表，才能进入 C 函数 `usertrap()`。

如果等进入 `usertrap()` 后才准备内核栈，就太迟了：执行 C 函数本身已经可能需要栈。因此这些信息必须在第一次进入用户态之前写好。

把工作分为两个时刻就容易理解：

```text
现在：内核准备自己的栈、页表值和处理函数地址，写入 trapframe 头部。
以后：用户执行 ecall，跳板保存用户寄存器，再读取已准备的内核信息。
```

本步对应 PDF 阶段一中“为进入内核准备环境”的部分。现在仍没有切入用户态，下面描述的陷入流程是将来要执行的流程。

### 5.2 栈到底是什么，为什么内核需要自己的栈

**栈（stack）**是一块按“后放入的内容先取出”的方式使用的内存。函数运行时，编译器可能用它存放局部变量、暂时保留的寄存器和返回地址。返回地址表示函数结束后应该继续执行哪条指令。并非每个局部变量都一定进栈，有些会放在寄存器中。

**`sp`（stack pointer，栈指针）**是普通寄存器，存放当前栈位置。可以把它理解成“栈现在用到哪里”的游标。函数开始时通常减小 `sp`，给自己留一块空间；函数结束时把 `sp` 加回去，归还这块空间。

当前启动时已经使用 `entry.S` 的 `boot_stack`，称为**启动栈**。本步另外在 `trap.c` 中分配 `trap_stack`，供以后从用户态进入内核时使用。再往后，用户程序还会有自己的**用户栈**。

| 栈 | 用途 | 当前情况 |
|---|---|---|
| 启动栈 `boot_stack` | 从机器启动到运行当前 `main()` | 已在使用 |
| 内核陷入栈 `trap_stack` | 以后在 `usertrap()` 等内核处理函数中运行 | 本步分配并记录栈顶，尚未切到它 |
| 用户栈 | 用户程序执行自己的函数 | 后续创建 |

用户能修改自己的栈，也可能把自己的 `sp` 设置成无效地址。内核处理用户请求时，需要使用内核管理的内存，不能依赖用户提供的栈位置。为每个进程维护独立内核栈还涉及进程管理；现在只为第一份启动用户任务准备一块，后续会继续完善。

### 5.3 怎样分配栈，栈顶为什么在数组末尾之外

对应代码位于 `kernel/trap.c`：

```c
static uint8 trap_stack[2 * PGSIZE] __attribute__((aligned(16)));
```

`uint8` 表示一个 8 位无符号数，占 1 字节，因此这个数组就是一块连续的字节存储区。`PGSIZE` 是一页的大小，等于 4096 字节；`2 * PGSIZE` 是 8192 字节，即 8 KiB。两页是当前实现为首次陷入选择的栈容量，不表示 PDF 强制要求栈一定为两页。

这里的 `static` 使这块存储在内核运行期间持续存在，名称也只在此源文件中使用。它没有显式初值，被放进内核的 `.bss` 区域。它不是 `trap_init()` 的临时局部数组，因此函数结束后不会消失。

`__attribute__((aligned(16)))` 是告诉编译器：数组起始地址必须是 16 的倍数。RISC-V 的标准函数调用约定要求栈指针保持 16 字节对齐；本数组长度也能被 16 整除，所以数组末尾同样对齐。**调用约定**是编译器和汇编共同遵循的规则，例如参数放在哪些寄存器、哪些寄存器由谁保存、栈怎样对齐。

栈顶这样计算：

```c
tf->kernel_sp = (uint64)(trap_stack + sizeof(trap_stack));
```

`sizeof(trap_stack)` 返回整个数组的字节数 8192。这里数组元素恰好是一字节，所以指针加 8192 就向后移动 8192 字节。注意：若数组元素是 8 字节的 `uint64`，同样的指针加法就会移动 8192 × 8 字节。

本次构建实际分配的范围如下；以后新增代码或数据，链接地址可能变化：

```text
0x8000a000  ┌─────────────────────────┐  数组第一个字节
            │ 内核陷入栈，共 8192 字节 │
0x8000bfff  └─────────────────────────┘  数组最后一个字节
0x8000c000                              初始 sp，数组末尾之后

如果某函数要留出 32 字节栈空间：
sp 从 0x8000c000 减到 0x8000bfe0，使用 [0x8000bfe0, 0x8000c000)。
```

`[起点, 终点)` 表示包含起点、不包含终点。栈向低地址增长，所以一开始让 `sp` 指向尚未使用的上边界，再先减小它、后存数据。C 允许计算“数组末尾之后”的指针，但不能把该位置当成数组元素直接读写。这里仅把它作为初始栈位置。

### 5.4 四个内核字段各自存什么

`trap_init()` 在启动页表准备好之后调用。它通过：

```c
struct trapframe *tf = (struct trapframe *)TRAPFRAME;
```

访问第 3 步已经映射的现场页。**指针**保存地址；这里的强制类型转换告诉 C：“按 `struct trapframe` 的格式解释这个地址处的内存。”这行不会分配第二份现场，也没有把地址复制到另一个地方。`tf->kernel_sp` 表示通过指针找到现场，再访问其中名为 `kernel_sp` 的字段。

随后先把结构的 288 字节清零，再填写四个内核字段。清零循环把结构看成字节数组，逐字节写 0，是因为目前还没有引入内核通用的 `memset()`。只清结构大小，现场页剩余部分没有被这个循环使用。此初始化函数目前只在启动时调用一次；将来正在运行的用户现场不能随意再次整块清零，否则会丢失寄存器和返回地址。

| 字段 | 本步写入 | 用途 |
|---|---|---|
| `kernel_satp` | `r_satp()` | 以后让跳板恢复内核页表控制值 |
| `kernel_sp` | 内核陷入栈上边界 | 以后让跳板把 `sp` 换成内核栈 |
| `kernel_trap` | `(uint64)usertrap` | 以后让跳板跳到 C 处理入口 |
| `kernel_hartid` | `r_tp()` | 以后恢复内核使用的 CPU 硬件线程编号 |

`epc` 虽然也在前五项中，但它存的是用户的执行位置，本步暂时为 0。等准备首个用户程序时才设置入口；发生陷入后还需要把硬件 `sepc` 的内容保存到这里。它为 0 不表示现在可以从用户地址 0 开始执行。

#### 页表字段为什么保存 r_satp()，而不是直接保存页表地址

`satp` 是 CPU 的控制寄存器，决定地址怎样翻译。**控制寄存器**用于配置 CPU 行为，与普通的参数、算术寄存器用途不同。`r_satp()` 是本项目的读取辅助函数，内部用 `csrr` 读取该寄存器；名称里的 `r` 表示 read。

RV64 的 `satp` 同时包含地址翻译模式、地址空间编号和根页表的物理页号。**物理页号**是物理地址除以 4096 后的编号。本次根页表物理地址是 `0x80009000`，右移 12 位得到页号 `0x80009`。Sv39 模式编号为 8，放在最高四位；当前地址空间编号为 0，因此完整值是：

```text
satp = (8 << 60) | (0x80009000 >> 12)
     = 0x8000000000080009
```

跳板以后会把字段内容直接写回 `satp`，所以必须保存这个完整的控制值。如果只存 `0x80009000` 这个原始地址，CPU 会按 `satp` 的位格式解释它，得不到我们需要的 Sv39 页表配置。现在 `boot_vm_init()` 已启用页表，随后读取 `r_satp()` 就能取得正确值。

#### 把 usertrap 写进字段，是不是已经调用了它

不是。`(uint64)usertrap` 取得函数入口地址，将该地址保存成 64 位数；`usertrap()` 带括号才表示执行函数调用。可以理解成“记下目的地地址”和“现在出发”的区别。

本次函数入口地址是 `0x800004a4`。跳板以后会用 `ld t0,16(a0)` 取出此地址，再用 `jalr t0` 跳过去。`jalr` 是按寄存器中地址进行函数调用的指令，会同时记录返回地址；它不是按函数名查找目标，运行时只使用地址。

#### hart、mhartid 和 tp 是什么，为什么在启动汇编中设置

**hart（hardware thread）**是能独立执行指令、拥有自己寄存器状态的硬件执行线程。当前实验只让 hart 0 运行；hart 编号不是用户进程编号，也不是操作系统线程编号。

`mhartid` 是保存本 hart 编号的机器级控制寄存器。当前内核 C 代码在 S 态运行，不能直接读取这个 M 态寄存器。因此在 `entry.S` 仍处于 M 态时：

```asm
csrr t0, mhartid   # 读取本硬件线程编号
bnez t0, park      # 非 0 号线程进入等待
mv tp, t0         # 把编号留在普通寄存器 tp 中
```

`tp` 的通用名称是 thread pointer（线程指针），是普通寄存器。它的名字并不意味着硬件自动把 CPU 编号写到里面；本内核约定用它保存 hart 编号，所以必须由软件赋值。进入 S 态后，`r_tp()` 读取这个普通寄存器即可，当前结果是 0。

以后跳板先保存用户程序原来的 `tp`，再从 `kernel_hartid` 取出内核编号写到 `tp`。这也解释了为什么结构中既有 `tp` 又有 `kernel_hartid`：前者是用户现场，后者是内核运行约定。

### 5.5 初始化顺序与跳板怎样使用这些信息

当前 `main()` 的顺序为：

```c
boot_vm_init();  // 先使 TRAPFRAME 高地址能通过页表访问
trap_init();     // 再通过该地址填写现场头部
// 然后打印原来的 Lab1 输出
```

如果倒过来，写 `TRAPFRAME=0x3fffffe000` 时映射尚未启用，就无法到达我们准备的 RAM 页。这是两个函数之间的实际依赖，不是随意选择的顺序。

赠送 `uservec` 在保存用户寄存器后已有这些指令，不需要修改赠送文件：

```asm
ld sp, 8(a0)     # 现场偏移 8：内核栈顶
ld tp, 32(a0)    # 现场偏移 32：内核硬件线程编号
ld t0, 16(a0)    # 现场偏移 16：usertrap 地址
ld t1, 0(a0)     # 现场偏移 0：完整内核 satp 值
# 清地址翻译缓存、写 satp、再次清缓存
jalr t0          # 进入 C 函数
```

在这段中 `a0` 已被跳板设置成现场起点。`ld` 表示从内存加载一个 8 字节值到寄存器；例如 `8(a0)` 就是“现场起点加 8 字节处”。第 4 步确定字段位置，第 5 步填入字段内容，两步共同满足这些汇编的输入要求。

## 第 6 步：判断陷入原因，准备返回用户态

### 6.1 本步要解决什么问题，先看一个完整例子

前几步准备好了跳板、现场页和内核栈，但原来的 `usertrap()` 只会打印错误并停机。现在需要判断：这是用户主动请求服务，还是设备中断，还是用户程序出错？处理完正常请求后，又该告诉 CPU 从哪里、以什么权限继续？

假设用户代码以后包含：

```text
地址 0x1000：ecall           请求内核服务
地址 0x1004：下一条指令      请求处理完后应该从这里继续
```

未来实际发生这次陷入时，硬件记录 `scause=8`、`sepc=0x1000`，并把权限切到 S 态。跳板先保存普通寄存器、换到内核环境，再调用 C 函数。本步的 C 代码将保存返回地址、识别请求、把现场中的返回地址改成 `0x1004`，然后准备 `sret` 所需的状态。

本步将尚未实现的系统调用统一返回 `-1`。这表示“请求暂不支持”，不是让用户反复执行原来的 `ecall`，也不是已经实现 `getpid/write/exit`。那些具体服务按 PDF 阶段二继续做。

本步实现的调用关系为：

```text
usertrap()
  → handle_user_trap()       检查来源、保存地址、分类并处理
  → usertrapret(user_satp)
      → prepare_return()    准备下一次陷入入口、返回权限和地址
      → 跳板 userret        切用户页表、恢复普通寄存器、执行 sret
```

`handle_user_trap()`、`prepare_return()` 是自有 C 辅助函数，`static` 使它们只在 `trap.c` 中使用。把职责拆开能分别检查“处理结果”和“返回设置”。赠送汇编无需修改。正式启动目前仍停在 Lab1 输出后的等待循环，没有调用首次 `usertrapret()`；真实用户态往返留到下一小步。

### 6.2 四个控制寄存器先各记住一句话

**CSR（Control and Status Register，控制与状态寄存器）**是 CPU 内部用于配置行为、记录事件的特殊寄存器。普通寄存器 `a0/sp/t0` 装数据和地址，CSR 则告诉我们 CPU 发生了什么、接下来该怎样运行。辅助函数 `r_...()` 读取 CSR，`w_...()` 写入 CSR；内部通常分别使用 `csrr`、`csrw` 指令。

| 名称 | 先记住的作用 | 本步使用方式 |
|---|---|---|
| `scause` | 为什么进入内核 | 区分用户 `ecall`、外部中断和异常 |
| `sepc` | 陷入时记录的执行位置，也是 `sret` 的目标位置 | 先保存到现场，再写入处理后的返回地址 |
| `sstatus` | S 态相关状态，其中一些位控制返回权限和中断状态 | 检查来源，设置返回到 U 态所需的位 |
| `stvec` | 下一次交给 S 态的陷入从哪里开始执行 | 用户运行前指向 `uservec`，内核运行时指向内核诊断入口 |

名字开头的 `s` 表示 supervisor（监督级）。本机启动时已经通过 `medeleg/mideleg` 配置把可委托的异常和中断交给 S 态处理，所以用户 `ecall` 会走 S 态入口。这些寄存器是每个 hart 自己的一份硬件状态；它们并不是每个用户进程自动拥有一套的内存数据。

### 6.3 scause 怎样区分请求、中断和错误

**陷入（trap）**是异常或中断使 CPU 转入处理入口的总称。**异常（exception）**通常由当前正在执行的指令触发，如请求服务的 `ecall`、非法指令或错误的访存。它与当前指令有关，也叫同步事件。异常不一定表示程序犯错：`ecall` 就是正常的主动请求。

**中断（interrupt）**通常来自执行流程之外，如串口收到字符，与用户当前正在执行哪条指令没有直接关系，也叫异步事件。这是两类事件的来源差别，不表示我们可以不用保存寄存器。

RV64 的 `scause` 是 64 位。最高位为 0 表示异常，最高位为 1 表示中断；其余位表示具体原因编号。

```text
scause = 0x0000000000000008：最高位 0，编号 8，来自 U 态的 ecall
scause = 0x8000000000000009：最高位 1，编号 9，S 态外部中断
scause = 0x0000000000000002：最高位 0，编号 2，非法指令
```

代码使用 `cause == 8`，只匹配用户 `ecall`；不能只取低几位等于 8 就当成系统调用，否则会混淆不同事件。`1UL << 63` 的意思是把一个无符号整数 1 左移 63 位，得到最高位为 1 的数；`| 9` 用按位或加上原因编号，因此外部中断的完整值写成 `((1UL << 63) | 9)`。

目前处理如下：

```c
if (cause == 8) {
  tf->epc += 4;
  tf->a0 = (uint64)-1;
} else if (cause == ((1UL << 63) | 9)) {
  stop_trap("user external interrupt not connected yet");
} else {
  stop_trap("unexpected user trap");
}
```

外部中断已经有明确分类分支，但 UART/PLIC 的读取、确认和结束处理要在阶段三接上。现在遇到它会打印诊断并停机，不能说“中断已处理”。特别是不能什么都不做就返回：设备仍可能请求中断，CPU 会反复进入内核。

`tf->a0` 保存的是用户寄存器 `a0` 的现场，跳板以后会把它恢复给用户。调用约定规定 `a0` 存返回值，所以把错误值写到这里，而不是只在内核的局部变量中算出 `-1`。由于字段是无符号 64 位类型，`(uint64)-1` 的位模式为 `0xffffffffffffffff`；按有符号返回值解释时就是 `-1`。`a7` 中的调用号和其他参数目前不参与具体服务，模拟测试中保留不变。

### 6.4 sepc 与 tf->epc 有什么关系，为什么只能对 ecall 加 4

`sepc` 中的 `epc` 表示 exception program counter，即异常程序计数位置。**程序计数器 PC**表示正在执行的指令地址。发生用户 `ecall` 时，硬件把这条指令的地址记录到 `sepc`，并不会自动改成下一条指令。

`tf->epc` 则是 RAM 中现场结构的一个字段，是软件保存的副本。本步先执行：

```c
tf->epc = r_sepc();
```

这样内核可以在内存里保存、修改该用户的返回位置，而不把硬件 `sepc` 当作永久存档。后续如果处理别的陷入，硬件寄存器可能再次改变；每个进程的现场也需要分别记住自己的返回位置。

具体例子如下：

| 时刻 | 硬件 `sepc` | 内存 `tf->epc` |
|---|---|---|
| 捕获用户 `ecall` | `0x1000` | 尚未保存本次位置 |
| C 代码读取并保存 | `0x1000` | `0x1000` |
| 识别为 `ecall`，加 4 | `0x1000` | `0x1004` |
| 返回准备写回 `sepc` | `0x1004` | `0x1004` |
| 跳板执行 `sret` | CPU 使用 `0x1004` 继续执行 | 保留软件副本 |

为什么加 4？`ecall` 固定占 4 字节，因此下一条指令地址是当前地址加 4。当前编译配置支持压缩指令，有些指令占 2 字节，但不存在 2 字节版本的 `ecall`，所以这里的 4 是针对这条指令的确定长度，不能推广成“所有 RISC-V 指令都加 4”。

若不加，`sret` 回到 `0x1000` 又执行相同请求，形成重复陷入。若遇到中断却加 4，就可能跳过本来还应执行的用户指令；若遇到错误指令却无条件跳过，则可能掩盖错误。因此代码只在原因确实等于 8 时推进地址。

### 6.5 stvec 为什么要在两个入口之间切换

`stvec` 指定的是**陷入后首先执行的汇编地址**，不是 C 函数 `usertrap()` 的地址。用户运行时寄存器还属于用户，必须先经过 `uservec` 保存现场和换栈，不能直接进入普通 C 函数。

本步使用 direct（直接）模式，`stvec` 低两位为 0，表示交给 S 态的异常和中断都从这个入口开始，再由软件分类。`uservec` 的地址满足入口对齐要求。

这里有两种不同情况：

```text
用户正在运行 → stvec 应指向高地址跳板 uservec
内核正在运行 → stvec 应指向 kernel_trap_entry
```

内核已经换到自己的栈后，若发生错误，还继续走用户入口，跳板会把内核寄存器写进用户现场，覆盖本来应该恢复的用户数据。因此 `trap_init()` 和用户陷入的 C 处理部分都把入口切到 `kernel_trap_entry`。本步新增的自有汇编入口保持当前内核栈，直接转到 `kerneltrap_stop()` 打印并停机。

这个内核入口目前只是**致命错误诊断入口**，不是能保存全部现场并恢复运行的内核中断处理器。它没有完成可返回的寄存器保存协议，因此不能拿它处理正常时钟或串口中断后继续执行；对应支持在后续阶段完善。

在准备返回用户态时，`stvec` 要重新指向高地址跳板：

```c
w_stvec(TRAMPOLINE + ((uint64)uservec - (uint64)trampoline));
```

链接器告诉我们跳板物理页内各入口的位置。`uservec - trampoline` 计算入口相对页起点的偏移，再加到固定虚拟地址 `TRAMPOLINE` 上，就得到用户页表和内核页表都将映射的入口。它不是把整段代码复制一份。本项目当前 `uservec` 恰好位于跳板起点，偏移为 0，所以入口为 `0x3ffffff000`。

为什么不直接写物理地址 `0x80001000`？以后 CPU 仍使用用户页表刚进入跳板时，用户页表不应随意映射内核物理地址区；但我们会在两套页表中都映射这个固定高地址。使用高地址入口能与切页表过程配合。

### 6.6 sstatus 的 SPP、SIE、SPIE 分别做什么

**位（bit）**是寄存器中的单个二进制位置。`sstatus` 中许多位各有用途；不能为了设置一两个位就把整个寄存器随意写成 0，否则会抹掉其他状态。本步读取原值，只改变相关位。

| 位 | 含义 | 本步做法 |
|---|---|---|
| `SPP` | Supervisor Previous Privilege，记录陷入前权限，`sret` 用它决定返回到 U 还是 S | 检查用户陷入来源；返回前清成 0，选择 U 态 |
| `SIE` | Supervisor Interrupt Enable，S 态当前的中断总开关 | 返回准备开始就清成 0 |
| `SPIE` | Supervisor Previous Interrupt Enable，陷入时保存原 SIE；`sret` 会把它复制回 SIE | 返回前置成 1，准备返回后的 SIE 状态 |

发生交给 S 态的陷入时，硬件会记录此前权限到 `SPP`，把原 `SIE` 保存到 `SPIE`，并清零 `SIE`。因此真正从 U 态来的陷入应有 `SPP=0`。本步在 `handle_user_trap()` 开头检查：若 `SPP=1`，说明来源是 S 态，走了不匹配的用户处理入口，打印诊断并停机。

返回准备的代码是：

```c
intr_off();                  // 清当前 SIE，准备过程中保持关中断
uint64 status = r_sstatus();
status &= ~SSTATUS_SPP;       // 清 SPP，指定 sret 的目标权限为 U
status |= SSTATUS_SPIE;      // 置 SPIE，供 sret 恢复 SIE
w_sstatus(status);
w_sepc(tf->epc);
```

`&= ~掩码` 表示把指定位置清零、保留其他位；`|= 掩码` 表示把指定位置置 1、保留其他位。清 `SPP` **不会立刻让当前 C 代码降到 U 态**，它只是设置下一次 `sret` 的目标权限；真正的权限切换由 `sret` 执行。

为什么先清 `SIE`？返回准备会把 `stvec` 切成用户入口，但此时 CPU 还拿着内核寄存器。若这段准备过程中响应一个 S 态中断，就可能误用用户入口覆盖现场。因此要先关当前中断，再改入口、页表参数和返回状态。

`SPIE=1` 也不是“现在打开中断”，当前 `SIE` 仍为 0。`sret` 执行时才根据 `SPP` 返回相应权限，并把 `SPIE` 复制到 `SIE`。这里还要避免误解：U 态是否能被 S 态设备中断打断，还受中断委托、`sie`、PLIC 和设备配置等条件控制；`SIE` 是 S 态的开关，不能把它简单叫作“用户键盘开关”。更高权限中断在低权限运行时还有独立的硬件使能规则。具体中断链路会在阶段三逐项解释。

本步模拟测试还设置了无关的 `SUM` 位再做返回准备，确认它未被误清。`SUM` 控制 S 态访问带用户权限的数据页的许可，本步仅用它验证“保留其他状态”的行为；未来访问用户数据时再详细讲解其作用。

### 6.7 usertrapret 怎样把工作交给赠送 userret

本步定义 `usertrapret(uint64 user_satp)`。参数是完整的用户页表 `satp` 控制值，不是原始页表地址。首次进入用户态时，未来的启动代码会提供这个参数；后续陷入使用当前保存的 `active_user_satp` 返回原来的页表。目前只有一份启动用户现场，未来多进程必须分别记录各自页表，不能用这一个全局值代表所有进程。

`prepare_return()` 在当前内核页表下重新填写四项内核环境，确保**下一次**陷入也有正确的栈、页表、C 入口和 hart 编号。它不清零整个结构，也不覆盖用户寄存器。随后设置 `stvec/sstatus/sepc`。

`usertrapret()` 再计算返回入口：

```c
uint64 entry = TRAMPOLINE + ((uint64)userret - (uint64)trampoline);
((void (*)(uint64))entry)(user_satp);
```

当前 `userret` 在跳板页内偏移 `0x9c`，所以固定高地址入口为 `0x3ffffff09c`。第二行把这个地址解释成“接收一个 `uint64` 参数的函数入口”并调用它，称为**函数指针调用**。RISC-V 调用约定把第一个参数放到 `a0`，因此刚进入汇编时 `a0` 装的正是用户 `satp` 值。

赠送 `userret` 随后依次执行：同步指令缓存、切到用户页表并清地址换算缓存、通过 `TRAPFRAME` 恢复用户普通寄存器、最后执行 `sret`。恢复用户 `a0` 是靠近末尾的动作；在此之前 `a0` 曾先用来传用户页表值，再用来定位现场，不能提前恢复。

`sret` 根据准备好的 `sepc` 和 `SPP` 继续用户代码，**不是像普通 C 函数那样回到调用它的下一行**。因此头文件用 `noreturn` 告诉编译器该函数不会按普通调用方式返回，末尾的 `__builtin_unreachable()` 也表达这一约定。它们是编译器提示，本身不执行权限切换，真正切换仍靠赠送汇编中的 `sret`。

### 6.8 出错时打印的三个数怎样帮助定位问题

诊断统一打印 `scause/sepc/stval`：前者说明原因，第二个定位指令，第三个提供与原因有关的附加信息。**`stval`（Supervisor Trap Value）**常在访存错误中记录出问题的虚拟地址；对其他事件，它可能是 0 或其他规定的信息，不能把所有 `stval` 都解释成坏地址。

例如实际用户程序将来访问未映射的地址时，`sepc` 帮我们找到执行访存的指令位置，`stval` 帮我们找到它试图访问的地址。两个地址不必相同：一个是“哪条指令出错”，另一个是“它访问了哪里”。

停止函数先关中断，然后打印，最后一直执行 `wfi` 等待。**停机**在这里表示内核不再正常向前执行，也不会返回用户；不是让电脑物理断电。QEMU 本身仍在运行，所以还能通过 monitor 看寄存器和内存。

## 第 7 步：真正进入用户态，完成一次 ecall 往返

### 7.1 本步与上一步的验证有什么不同

第 6 步由测试代码写入控制寄存器，模拟“硬件已经完成陷入”的状态，验证 C 处理逻辑。本步让 CPU 真正执行用户指令，由硬件产生陷入，再走赠送汇编保存和恢复现场。我们要检查整个连接过程是否正确，而不只检查其中两个 C 函数。

暂时使用一个自有的最小汇编程序 `kernel/user_probe.S`，不加载 Shell，也不实现输出系统调用。它只做三件事：执行一次 `ecall`，把返回后的寄存器写到用户栈，最后写完成标记并循环等待。**probe** 在这里表示用于观察行为的小测试程序，不是操作系统要求的特殊程序类型。

```text
main 打印 Lab1 原有输出
  → 准备用户页表、代码页、栈和首次现场
  → usertrapret → userret → sret
  → U 态执行地址 0x1000 的 ecall
  → 硬件陷入 → uservec → usertrap
  → 返回位置改为 0x1004，a0 写为 -1
  → usertrapret → userret → sret
  → U 态从 0x1004 继续，存寄存器、写完成标记、循环
```

首次进入 U 态也使用 `userret/sret`。名称叫“返回”，但硬件不要求此前一定运行过用户代码；只要事先准备好目标权限、指令位置和寄存器，便可以通过这条路径首次进入 U 态。

### 7.2 用户页表为什么要另建，虚拟地址和物理地址怎样对应

**用户页表**是用户程序运行时使用的地址翻译表。本步新增 `kernel/user_boot.c`，分配一套独立的三级 Sv39 页表。当前内核页表粗略映射了内核和设备区域，不能把它直接变成允许用户访问内核全部内存的页表。

虚拟地址是程序指令里使用的地址，物理地址是 RAM 中实际存储位置；页表将前者转换成后者。程序看到 `0x1000`，并不意味着指令实际放在物理 RAM 的 `0x1000`。QEMU 的 RAM 在 `0x80000000` 一带，我们把 RAM 中的一页映射成用户看到的低地址。

本次链接得到的实际布局如下。物理地址以后可能随构建变化，固定虚拟地址则由本测试规定。

| 用户页表中的虚拟范围 | 本次对应的物理内存 | 访问权限与用途 |
|---|---|---|
| `[0x0000, 0x1000)` | 没有映射 | 空指针附近无可访问页 |
| `[0x1000, 0x2000)` | `probe_code`，从 `0x8000d000` 起 | 用户可读、可执行，不能写；测试代码 |
| `[0x2000, 0x3000)` | 没有映射 | 用户栈下方的空页 |
| `[0x3000, 0x4000)` | `probe_stack`，从 `0x8000c000` 起 | 用户可读写，不能执行；用户栈 |
| 从 `0x3fffffe000` 起的一页 | `boot_trapframe`，从 `0x80006000` 起 | 仅 S 态可读写；寄存器现场 |
| 从 `0x3ffffff000` 起的一页 | `trampoline`，从 `0x80001000` 起 | 仅 S 态可读、可执行；跳板 |

表中的区间含起点、不含终点。**未映射**表示没有有效的地址换算条目，访问时会产生页故障；不表示该地址处一定存着 0。栈下方的空页可以作为**保护页（guard page）**，栈向下越过正常范围时不能继续无声地覆盖相邻区域。本步检查了页表条目，尚未故意越界触发保护页错误。

例如用户从 `0x1004` 取指，页内偏移是 4，页表选择代码页 `0x8000d000`，得到物理地址 `0x8000d004`。页表映射的是整页，所以 `0x1000` 到 `0x1fff` 都对应同一物理页内的不同偏移。

本步的用户代码页和栈页是自有数组，预留在内核 `.bss` 中，起始地址按 4096 字节对齐。它们属于专门保留的存储，复制进去不会覆盖现有函数。当前内核末尾为 `0x80013010`；PDF 阶段四要求在内核末尾之后装载 Shell 等程序，那是后续正式装载器的工作，本步只是用预留测试页验证通道，没有完成 Shell 装载。

### 7.3 页表中的权限标志具体限制什么

**PTE（Page Table Entry）**是页表中的一个条目。非叶条目指向下一层页表，叶条目指向最终物理页并规定权限。这里的“叶”表示沿表逐层查找到了终点，不再继续查下一层。

| 标志 | 含义 |
|---|---|
| `V` | Valid，条目有效 |
| `R` | Read，可读取 |
| `W` | Write，可写入 |
| `X` | Execute，可作为指令执行 |
| `U` | User，允许 U 态访问该页 |
| `A` | Accessed，页已被访问的状态位 |
| `D` | Dirty，页已被写入的状态位 |

本步预先设置 `A`，对允许写的页也设置 `D`，避免这次小测试依赖处理访问位/修改位的页故障机制。它们是硬件地址翻译状态的一部分，不是系统调用号。

用户代码带 `R/X/U`，用户栈带 `R/W/U`。跳板和现场页虽然也出现在用户页表中，却**不带 `U`**。为什么不矛盾？刚陷入时 CPU 已经变成 S 态，但 `satp` 还没有切到内核页表；因此需要在当前用户页表中找到 S 态才能用的跳板和现场。映射存在，只代表地址可以翻译，能否使用还要结合权限位和 CPU 当前权限。

同一份现场物理页必须出现在两套页表的 `TRAPFRAME` 位置。本步通过 `boot_trapframe_pa()` 取得既有现场的物理地址，再建立用户侧映射。该函数只提供地址，并没有分配另一份现场。如果用户页表和内核页表指向不同物理页，跳板保存的现场和 C 代码读取的现场就会错开。

用户页表也没有建立 `0x80000000` 一带的内核恒等映射。仅有用户代码、栈以及上述两个 S 态跳板相关页；不能因为内核能用某个地址，就认定用户也能用它。本步测试核对了这些映射，不代表已完整验收所有未来多进程的权限边界。

### 7.4 第一次进入用户态，寄存器从哪里来

CPU 第一次执行 `userret` 时，还没有真实用户陷入保存的现场，所以要由内核先构造一份**初始现场**。可以理解成内核为第一次运行准备的寄存器清单。

```c
tf->epc = 0x1000;   // 首条用户指令的位置
tf->sp = 0x4000;    // 用户栈上边界，栈向下增长
tf->a0 = 123;       // 请求前的测试参数
tf->a7 = 999;       // 不支持的调用号，期待返回 -1
usertrapret(MAKE_SATP(user_root));
```

`user_root` 是用户根页表。`MAKE_SATP` 把 Sv39 模式和物理页号组合成完整控制值；本次根页表物理地址为 `0x80012000`，用户 `satp` 为 `0x8000000000080012`。内核 `satp` 仍为 `0x8000000000080009`。两值不同，所以本次确实要切换两套页表，而不是给同一张表换一个名字。

用户栈范围为 `[0x3000, 0x4000)`，初始 `sp` 指向上边界 `0x4000`，满足 16 字节对齐。实际物理页是 `[0x8000c000, 0x8000d000)`。内核陷入栈则是 `[0x8000a000, 0x8000c000)`，两块内存相邻但不重叠；前一块的上边界不属于前一块。

为了验证寄存器，本步还给 `x1` 到 `x31` 赋不同的测试值 `0x101` 到 `0x11f`，再覆盖 `sp/a0/a7` 的专用值。**测试值**是方便识别丢失或串位的数据，不是用户程序真正需要的业务参数。现场中从偏移 40 开始恰好按这 31 个寄存器的顺序排列，每项 8 字节，这个约定已经在第 4 步核对。

例如用户 `tp` 初始为 `0x104`，内核的 hart 编号为 0。如果陷入时正确切换内核 `tp`，返回时却忘了恢复用户 `tp`，用户快照就会出现 0 而不是 `0x104`。给出不同的值，能看见这种错误。

测试程序完全使用自有汇编，没有调用用户 C 函数，因此不需要把测试用的 `gp/ra` 设置成某个真实 C 程序的运行环境。将来加载赠送程序时，要按那个程序的启动与链接约定准备现场，不能直接沿用这些测试值。

### 7.5 为什么要复制代码，复制后为何不用修改其中地址

`user_probe.S` 的指令先作为一段只读内容嵌在内核镜像中，标记为 `user_probe_start` 到 `user_probe_end`。`user_boot.c` 计算长度，确认不超过一页，再逐字节复制到预留的 `probe_code` RAM 页。

本次原内容地址是 `0x80003708` 到 `0x800037a0`，总长 `0x98`，即 152 字节。程序以后从用户虚拟地址 `0x1000` 执行复制后的字节；原镜像中的副本不直接给用户执行。

这份小程序只包含 `ecall`、以 `sp` 为基准的存储、固定用户地址常量和页内的相对跳转。相对跳转表达“从这条指令往前/后移动多少字节”，整段复制后距离不变，所以仍正确。一般用户程序可能包含更多地址引用，不能由这份小程序推断任意代码都能随意搬到任意位置；后续装载器按赠送链接规则处理。

`.option norvc` 让本测试使用固定的 4 字节指令，便于把地址和源代码对应起来；`.option norelax` 禁止对这段汇编使用相关的链接松弛优化。**链接松弛**是链接器根据最终位置替换或缩短指令序列的一类优化，本测试选择固定形式便于观察。复制完指令后，赠送 `userret` 中的 `fence.i` 同步指令读取，使 CPU 能执行新写入的内容。

### 7.6 用户程序如何证明寄存器已恢复，而不是只看内核的副本

程序第一条指令就是地址 `0x1000` 的 `ecall`。返回时，地址 `0x1004` 的第一条存储指令开始记录寄存器：

```asm
ecall
sd ra, -256(sp)
sd sp, -248(sp)
sd gp, -240(sp)
sd tp, -232(sp)
# 后面继续依次存完其余寄存器
```

`sd` 将一个 8 字节寄存器值写到内存。`-256(sp)` 表示 `sp` 中地址减 256，此时 `sp=0x4000`，目标为 `0x3f00`，仍在用户栈页内。这些指令只读寄存器并存数据，不会先把它们改作临时变量。连 `sp` 自己也保持原值写入快照，因此检查得到的就是恢复后的真实值。

31 项共占 `31 × 8 = 248` 字节，存放在 `[0x3f00, 0x3ff8)`。剩下的 `[0x3ff8, 0x4000)` 放完成标记。31 项记录完成后，程序才使用 `t0/t1` 写标记：

```asm
li t0, 0x3ff8
li t1, 0x50415353
sd t1, 0(t0)
user_probe_done:
    j user_probe_done
```

`li` 是加载立即数的汇编写法，数字直接写在指令序列中；`j` 是跳转。`0x50415353` 是我们约定的数值标记，按十六进制分组可记成字符 PASS，并不是内核打印的一行字符串。工具读到标记，才继续核对完整快照。

最后停在用户地址 `0x1094` 的自循环。用户程序不使用内核里常见的 `wfi`：这条指令在低权限下的行为受机器配置限制，这里用普通跳转等待即可。QEMU 测试脚本检查完后会结束模拟器；手动 `make qemu` 时，这个程序会持续循环，暂时没有 Shell 提示符。

此时 CPU 当前的 `t0/t1` 已被用来写标记，不能再拿它们的当前值判断陷入前现场。我们比较的是**用户刚返回时写出的快照**，同时对照内核现场页。预期 30 项保持初值，`a0` 按处理结果变成 `-1`。所以“31 项检查通过”表示每项都符合协议，不表示返回值寄存器也必须保持请求前的 123。

### 7.7 页表切换时，为什么没有把跳板从脚下抽走

首次返回和陷入后返回，都在高地址 `userret` 内切页表。内核页表和用户页表的 `TRAMPOLINE` 指向同一个跳板物理页；切换 `satp` 后，当前高虚拟地址仍能翻译到同样的指令。

进入内核的方向也是一样：CPU 从 U 态切到 S 态，仍暂时使用用户页表，从高地址 `uservec` 保存现场，读取内核栈和内核 `satp`；然后切到内核页表，继续高地址跳板，最后跳到内核 C 代码。

```text
用户页表下的 TRAMPOLINE ─┐
                         ├─ 都找到物理跳板页 0x80001000
内核页表下的 TRAMPOLINE ─┘

用户页表下的 TRAPFRAME  ─┐
                         ├─ 都找到物理现场页 0x80006000
内核页表下的 TRAPFRAME  ─┘
```

页表切换前后执行的是同一份机器指令；相同高地址映射解决了“切换过程中还能从哪里继续取指”的问题。两边现场映射指向同一页，则解决了“汇编和 C 是否读写同一份寄存器存档”的问题。

## 第 8 步：系统调用分发与 getpid，用具体例子看参数和返回值

### 8.1 为什么已经能 ecall，仍然需要分发

第 7 步修好了“请求进入内核，再返回”的通道，但当时任何用户 `ecall` 都得到 -1，内核还不会提供具体服务。本步需要回答两个不同问题：这次为什么进入内核？用户进入内核后希望内核做什么？

第一个问题由 `scause` 回答，例如 8 表示 U 态 `ecall`。第二个问题由用户约定放在 `a7` 的**系统调用号**回答。**分发（dispatch）**就是根据调用号，把请求交给对应的内核处理函数。

可以把 `ecall` 想成走进服务大厅，`a7` 是你取的业务号码，`a0/a1/a2` 是提交的材料，返回后的 `a0` 是办理结果。这个比喻只帮助记忆：真实代码没有大厅或纸质表格，只有寄存器、现场内存和函数调用。

三个具体请求进入内核时都可能是 `scause=8`，但业务不同：

| 用户想做什么 | scause | a7 | 内核据什么区分业务 |
|---|---|---|---|
| 查询自己的进程编号 | 8 | 11 | 11 对应 getpid |
| 输出几个字符 | 8 | 16 | 16 对应 write，后续实现 |
| 请求不存在的服务 | 8 | 999 | 没有匹配项，返回 -1 |

**8 是陷入原因编号，11 是系统调用编号**，它们属于不同的编号体系。不能把 `scause == 11` 当作 getpid，也不能以为 `ecall` 指令本身已经写明了 getpid。

### 8.2 getpid、进程、PID 与 hart 的区别

`getpid` 可以拆成 get + PID，表示获取当前进程标识。**进程（process）**是操作系统管理的一次程序运行实例，通常包含编号、地址空间、寄存器现场和运行状态。程序文件更像一份执行说明，进程则是按说明正在运行的一份实例。

例如，同一个 hi 程序以后运行两次，可以形成两个不同的运行实例，得到不同 PID。它们使用同一份程序逻辑，不意味着是同一个进程。

**PID（Process ID）**是内核用于区分这些运行实例的编号。当前尚未实现完整进程管理，本步只为唯一的启动用户任务记录身份，分配 PID 1：

```c
struct proc {
  uint64 pid;
};

static struct proc boot_process;

void proc_boot_init(void)
{
  boot_process.pid = 1;
}
```

`struct proc` 是一条进程记录的类型，现在只有 pid 字段。`boot_process` 是具体的一条记录，静态存储在内核中。用户启动函数在进入 U 态前调用 `proc_boot_init()`，明确赋值。这里的 1 是本内核给首个任务选择的身份，不是读 CPU 寄存器算出来的。

再用一个例子区分 PID 与 hart：

```text
当前实际情况：hart 0 执行用户任务，用户任务的 PID 是 1。
以后可能的情况：hart 0 先执行 PID 1，随后切换去执行 PID 2。
```

后半段只是未来调度的示例，目前没有实现 PID 2、任务切换或调度器。**hart 编号标识执行指令的硬件线程，PID 标识被执行的程序实例**，两者不必相同。任务重复问自己的 PID，两次应得到相同结果；并不会因为查询一次就创建一个新进程或让编号加一。

本步 `myproc()` 返回 `&boot_process`，即唯一任务记录的地址。`sys_getpid()` 读取：

```c
return myproc()->pid;
```

`->` 表示通过指针访问字段，可理解成“找到当前任务那条记录，再拿出其中的 pid”。`getpid` 是用户接口名称，`sys_getpid` 是内核服务函数名称，`myproc` 是本内核取得当前任务记录的辅助函数，这几个名称的职责不同。

目前该记录不是完整进程表，也没有 PID 分配器、状态变化或回收逻辑。后续 fork、wait 和多进程支持时，需要逐进程管理地址空间、栈、现场与身份，不能永久让 myproc 返回同一条记录。

### 8.3 11 从哪里来，用户怎样发出 getpid 请求

赠送 `kernel/syscall.h` 定义：

```c
#define SYS_getpid 11
#define SYS_write  16
```

`#define` 是预处理宏，编译前把名字替换成规定的值。`SYS_getpid` 让代码表达服务含义，最终机器代码仍用数字 11。用户和内核必须使用同一份编号协议，不能因为“这是第一个实现的调用”就把 getpid 改成 1；协议中 1 已属于 fork。

赠送 `user/usys.pl` 会生成用户侧的小汇编入口，例如：

```asm
getpid:
    li a7, SYS_getpid
    ecall
    ret
```

这样的入口常叫**系统调用桩（stub）**，也可理解为一个很短的包装函数：先准备协议要求的寄存器，再触发陷入，返回后结束普通函数调用。它不是在 U 态直接调用内核里的 `sys_getpid()`。

用未来的用户 C 代码看完整过程：

```c
int id = getpid();
// 请求成功后，本任务的 id 应为 1。
```

用户 C 的函数调用先进入用户侧桩；桩将 a7 设为 11，执行 ecall。返回 U 态后，a0 已经是结果 1，桩执行 ret 回到用户 C，编译器按照函数返回值约定取得 a0，赋给 id。

本步实际使用自有测试汇编中的 `li a7,SYS_getpid; ecall` 验证服务，还没有加载执行完整赠送 hi 程序。上面的用户 C 与桩用于说明以后相同协议怎样被 C 程序使用，不代表 hi 已经通过最终验收。

### 8.4 内核分发代码怎样逐行工作

新增的 `kernel/syscall.c` 包含协议头和进程记录头，定义：

```c
uint64 syscall_dispatch(struct trapframe *tf)
{
  switch (tf->a7) {
  case SYS_getpid:
    return sys_getpid();
  default:
    return (uint64)-1;
  }
}
```

`tf` 指向刚由跳板保存的用户现场。不能直接把 C 函数当前的 a7 当成用户调用号，因为进入 C 后编译器可能已经把普通寄存器用于别的计算；应当读取 RAM 中保存的 `tf->a7`。

**switch** 是 C 的多分支选择语句。先求 `tf->a7` 的值，与各个 case 比较，匹配 11 时调用 sys_getpid。`return` 结束当前 C 函数，并将数值交回调用者；这里不用 break，是因为已经 return 了。没有匹配项时进入 default，得到 -1。

调用者仍是 `trap.c`：

```c
tf->epc += 4;
tf->a0 = syscall_dispatch(tf);
```

这里的两个动作分别是：设置用户下一条执行位置，设置用户返回值。分发器的普通 C return 只是回到 trap.c；之后仍要执行 usertrapret 和跳板，真正用 sret 回到用户。这再次说明 **C 函数 return 与权限返回 sret 不是同一个操作**。

新 `syscall_dispatch.h` 只声明自有函数接口，赠送 `syscall.h` 只规定调用号，两份头文件用途不同。本步没有改赠送编号或用户桩生成器。构建文件加入 syscall.o 和 proc.o，并设置头文件依赖，使相关源码或声明变化后重新编译。

### 8.5 例子一：请求前 a0 是 123，为什么结果仍然是 1

`getpid` 不需要用户参数。用户已经由当前执行状态确定是谁，内核读取当前任务记录即可。因此即使请求前 a0 是 123、456 或上次调用留下的 -1，getpid 都应返回同一个任务的 PID 1。

逐步追踪一次请求：

| 时刻 | 用户现场 a7 | 用户现场 a0 | 正在发生什么 |
|---|---|---|---|
| 用户准备 getpid | 11 | 任意旧值 | 用户不需要给 getpid 提供参数 |
| 跳板保存现场 | 11 | 同样的旧值 | 用户寄存器进入 RAM 中的 tf |
| 分发器匹配 | 11 | 尚未改写 | 选择 sys_getpid |
| 服务读取任务记录 | 11 | 尚未改写 | boot_process.pid 为 1 |
| trap.c 写回结果 | 11 | 1 | 结果存到用户 a0 的现场 |
| 跳板恢复到 U 态 | 11 | 1 | 用户得到返回值 |

其中 a7 负责选择业务，a0 在返回时负责结果，不能把 a7=11 当作“返回 PID 11”。把调用号和返回值分别记成“我要办哪件事”和“这件事办完得到什么”，比较容易区分。

### 8.6 例子二：错误调用后，为什么还能继续 getpid

假设程序先请求 999 号服务。协议中没有它，分发器走 default，返回 -1。与此同时，返回地址仍然跳过当前 ecall，所以程序可以继续执行下一条指令，再发出 11 号请求，得到 1。

```text
第一次：a7=999 → default → a0=-1 → 返回下一条指令
第二次：a7=11  → sys_getpid → a0=1 → 返回下一条指令
```

非法调用号属于请求内容不受支持，不等同于非法 CPU 指令。ecall 本身是合法指令，所以未知调用不能直接套用“非法指令，诊断停机”的处理；这里用确定错误值让用户继续运行。

调用号 0 也没有定义，同样得到 -1。write 的编号 16 已定义，但本步尚未实现其服务，所以也得到 -1。**编号已定义**只意味着接口合同中存在该服务，不能据此认定当前实现已经支持它。下一步接通 write 后，16 号分支会执行真实输出逻辑。

### 8.7 例子三：为什么一个低位等于 11 的大数不应该调用 getpid

用户寄存器是 64 位，测试值 `0x10000000b` 的完整十进制值是 4294967307，而其低 32 位恰好等于 11：

```text
完整值：0x000000010000000b
取低 32 位后：0x0000000b = 11
```

如果内核先写 `int number = tf->a7`，就可能截断高位，把无效的大数误识别成 getpid。本步直接 switch 完整的 uint64 字段，只有整个值等于 11 才匹配；这个大数应返回 -1。

这个例子帮助理解**截断（truncation）**：把较宽的数据放到较窄的类型里，高位信息可能丢失。此处不需要用户申请 64 位编号业务，只是要避免不支持的请求变成另一件有效请求。实际测试明确检查了这一边界。

### 8.8 例子四：同样使用 a0，write 为什么还需要更多参数

getpid 无参数，只有返回值。以后 write 则需要告诉内核输出到哪里、数据从哪里取、取多少字节。例如：

```c
write(1, "Hi\n", 3);
```

按当前接口约定，用户请求时 a0=1，a1=字符串的用户地址，a2=3，a7=16；返回时 a0 会被改成结果，例如成功写出 3 个字节就返回 3。**参数**是请求输入，**返回值**是处理输出；同一个寄存器可以在不同时间承担不同角色。

这里的 1 是文件描述符，通常表示标准输出，并不是 PID 1，也不是 hart 1。不同字段中出现相同数字不表示含义相同。文件描述符及缓冲区会在下一步详细解释。

这段 write 目前只是接口示例，本步实际的 16 号调用仍返回 -1。而且我们已经启用了独立用户页表，未来用户字符串的虚拟地址不能直接当成内核当前页表下的指针；必须按用户映射找到真实内存并检查长度与权限。下一步会用具体地址例子解释数据怎样跨这条边界。

### 8.9 本步测试怎样安排，六次调用分别证明什么

测试先保留第 7 步的 999 号调用及完整 31 项寄存器快照，再追加五次请求；快照完成之前不使用寄存器作为新的临时变量，原寄存器往返检查仍有意义。

| 顺序 | 本次 ecall 地址 | a7 | 期望 a0 | 检查目的 |
|---|---|---|---|---|
| 1 | `0x1000` | 999 | -1 | 原有往返和全部寄存器恢复 |
| 2 | `0x1084` | 11 | 1 | getpid 服务接通 |
| 3 | `0x1098` | `0x10000000b` | -1 | 完整 64 位调用号不会被截断成 11 |
| 4 | `0x10a4` | 0 | -1 | 未定义编号容错 |
| 5 | `0x10b0` | 16 | -1 | 已定义但未实现的服务容错 |
| 6 | `0x10bc` | 11 | 1 | 错误调用后仍能处理正常请求，PID 保持不变 |

后五次请求返回后，各自把结果存进用户栈 `[0x3e00, 0x3e28)`。例如 getpid 的第一份结果写在 `sp-512=0x3e00`，第二份错误结果写在 `sp-504=0x3e08`，两处相差 8 字节，一个 uint64 的大小。它们与原快照 `[0x3f00, 0x3ff8)`、完成标记 `0x3ff8` 不重叠。

最后一次 ecall 的地址为 `0x10bc`，所以最终 sepc 和现场 epc 应为 `0x10c0`，最后现场 a7=11、a0=1。初始寄存器快照仍来自第一轮，里面 a7=999、a0=-1；不能拿最后一次现场与第一轮快照机械地要求完全相等。检查脚本区分了两个时刻。

## 第 9 步：write 输出、参数解包与用户内存读取

### 9.1 先从 write(1, "Hi\n", 3) 的三个参数理解请求

本步实现 PDF 阶段二的 write。**write** 表示把一段指定长度的数据写到指定输出目标；它不会替用户把数据变成字符串，也不会自动寻找字符串结束位置。

```c
int result = write(1, "Hi\n", 3);
```

| 部分 | 本例值 | 意思 |
|---|---|---|
| 第一个参数 fd | 1 | 输出目标编号，当前表示标准输出 |
| 第二个参数 buf | "Hi\n" 的用户地址 | 从哪里取数据，不是直接传三个字符本身 |
| 第三个参数 n | 3 | 读取并输出 3 字节 |
| 返回值 result | 成功时 3 | 实际完成的字节数；本步出错统一为 -1 |

**文件描述符（file descriptor，fd）**是程序用来指代输入输出目标的小整数。通常 0 表示标准输入，1 表示标准输出，2 表示标准错误。**标准输出**是正常结果的默认去处，**标准错误**是诊断信息的默认去处。当前两者都接到同一个 UART 串口，并未实现完整文件描述符表、文件或管道；不能因此认为今后的文件描述符也都等同于串口。

这次只允许 fd 为 1 或 2。`write(0, buf, 3)` 返回 -1，因为本阶段不把标准输入当作可写目标；`write(99, buf, 3)` 也不支持。fd=1 与 PID=1 是不同含义：一个标识输出目标，一个标识进程。

`"Hi\n"` 对应三个数据字节 H、i、换行。C 字符串通常还带一个结尾的 `\0`，但 n=3 不包含这个结尾。若调用 `write(1, "Hi\n", 2)`，按接口应只输出 Hi 并返回 2，不会自动补换行；这个两字节变体是理解接口的例子，本次真实测试使用三字节版本。

### 9.2 参数怎样放进寄存器，为什么 a0 一会儿是 fd 一会儿是结果

赠送调用号表规定 SYS_write=16。用户侧准备：

```text
a7 = 16       请求 write 服务
a0 = 1        第一个参数，标准输出
a1 = 0x3000   第二个参数，用户缓冲区地址
a2 = 3        第三个参数，字节数
ecall         进入内核
```

跳板把它们保存到 tf。新增 `argraw(tf, index)` 按参数序号读取现场：0 读 a0，1 读 a1，2 读 a2。**参数解包**就是从约定位置取出用户请求的数据；raw 表示这里先取得原始 64 位值，然后由具体服务解释并检查，不表示它已是可信的内核指针。

```c
uint64 fd = argraw(tf, 0);
uint64 address = argraw(tf, 1);
uint64 length = argraw(tf, 2);
```

注意参数序号从 0 开始，调用者眼中的“第一个参数”对应 index=0。写成功后分发器返回 length，trap.c 把结果写到 tf->a0，跳板恢复给用户。因此同一个 a0 在不同时间承担不同角色：

```text
请求前 a0=1：我要写到标准输出。
返回后 a0=3：本次成功写出 3 字节。
```

其他请求失败时返回后 a0=-1。这不表示目标 fd 被改成 -1 后继续写，而是这次请求已经结束，寄存器现在装返回值。

### 9.3 为什么不能直接把 a1 强转成 char* 就读取

当前用户与内核使用不同页表。用户 `0x3000` 经用户页表找到 probe_stack 的 RAM 页；内核当前页表对低地址使用的是另一种映射，数字相同不代表找到同样的内存。

可以把地址理解成“某张地图上的坐标”。同一个坐标放在不同地图上，可能对应不同地点。CPU 切到内核页表后，内核不能拿用户坐标在自己的地图上直接找数据；应先参考该用户的地图取得真实位置。

本步在唯一启动任务记录中增加 pagetable 字段，保存用户根页表地址。启动准备建立映射后执行 `myproc()->pagetable = user_root`。**字段存的是页表地址**，不是用户字符串地址，也不是完整 satp 值；它用于内核手动查表。

例子：用户缓冲区从虚拟地址 `0x3000` 开始，前三个字节位于该页内偏移 0、1、2。页表告诉内核 probe_stack 的物理页起点，随后内核通过已有 RAM 恒等映射读取这三个物理位置。具体物理地址随链接变化，验收工具从符号表读取，不把旧步骤的物理地址固定写死。

本次该物理页起点仍为 `0x8000c000`，可把请求展开成下面这张表：

| 用户虚拟地址 | 对应物理地址 | 字节十六进制 | 内容 |
|---|---|---|---|
| `0x3000` | `0x8000c000` | `48` | H |
| `0x3001` | `0x8000c001` | `69` | i |
| `0x3002` | `0x8000c002` | `0a` | 换行 |
| `0x3003` | `0x8000c003` | `00` | 结尾零，本次 n=3 不读取 |

copyin 把前三项复制到内核 buffer[0..2]，UART 再发送这三个值。这能具体区分“指针 0x3000”“指针指向的字符 H”和“最终返回字节数 3”。

因此新增 `user_mem.c/user_mem.h` 提供两项操作：

- `user_readable`：检查整段用户范围是否可读。
- `user_copyin`：把用户地址对应的数据复制到内核缓冲区。copyin 的 in 指“进入内核”，不是读取键盘；反方向把结果放进用户缓冲区通常称为 copyout，尚未在本步实现。

本步走物理页的内核映射读取，不需要把 S 态切回用户页表，也不需要打开 SUM 后直接按用户虚拟地址读。

### 9.4 怎样逐层查页表，同时检查访问权限

`user_page_pa` 从用户根页表开始，使用虚拟地址的三个索引依次查第 2、1、0 层。没有有效 V 位就失败；非叶条目指向下一层，叶条目指向最终物理页。

本步用户映射只使用 4 KiB 叶页，所以只接受第 0 层叶条目；高层的大页叶条目不支持。虽然启动内核映射用了大页，此函数查的是独立用户页表，两者用途不同。查到的下一层地址和数据页地址还必须落在内核可访问的 RAM 范围内。

用于 write 的源数据必须同时有 U 和 R：U 表示用户允许访问，R 表示可以读取。write 是把数据送往输出设备，内核对源缓冲区的动作是**读取**，所以不要求源页有 W。

这带来两个容易误解的例子：

```text
用户代码页：R/X/U，没有 W。可作为 write 的只读源缓冲区。
用户现场页：R/W，但没有 U。不能作为用户 write 的源缓冲区。
```

第二种虽然内核自己可以读，也虽然出现在用户页表里，仍不能替用户输出：用户请求不能越过自己的权限边界。真实测试对此分别验证了成功和拒绝。

### 9.5 例子：页尾只剩一个字节，为什么 n=2 会被拒绝

用户栈页范围为 `[0x3000, 0x4000)`，上边界不属于这一页。

```text
write(1, 0x3fff, 1)：本例范围只在栈页内，按映射可读取。
write(1, 0x3fff, 2)：需要读取 0x3fff 和 0x4000，第二页没有映射。
```

本次真实测试第二种，返回 -1 且没有输出任何前缀字节；第一种用于对照理解范围，没有单独执行。

检查长度时，代码计算当前页还剩多少字节：`4096 - 页内偏移`。例如 0x3fff 的页内偏移为 4095，所以只剩 1 字节。处理完这一段，再查下一页，而不是只检查起点后就认定整个缓冲区有效。

系统调用先检查**整个范围**，成功后才输出。这样在当前单任务、页表不会并发改变的实现中，后续页无效不会导致先输出一部分再失败。以后存在多线程或并发改映射时，还需要另外考虑查表与使用之间的同步，不能把本步规则当作完整并发保证。

`user_readable` 还先检查 address < MAXVA、length <= MAXVA-address。先做减法比较，可以避免直接算 address+length 发生整数回绕。例如极大的非法地址加长度可能绕回很小的值，不能因为结果小就误认范围有效。当前真实测试覆盖空地址、无用户权限页和跨到未映射页；极端回绕不是独立运行用例。

### 9.6 长度为零、长度为负、数据中有零字节分别怎样理解

write 的长度按本阶段非负 int 范围接受，最大为 0x7fffffff。用户传 -1 时，64 位现场可能是全 1，超过上限，所以返回 -1；不会把它当作“输出非常多字节”。

`write(1, 0, 0)` 则返回 0，不读取任何内存、也不输出任何内容。长度为零时不需要验证这个缓冲区能否解引用；但 fd 仍必须是支持的输出目标。实际测试的空地址加零长度通过。

write 按字节长度工作，不按字符串终止符工作。假设用户有字节序列 `A、\0、B` 并请求写 3 字节，接口应输出三个原始字节，零字节也包含在返回长度中；终端可能看不见零字节，但它仍是数据。这个二进制例子用于解释实现语义，本步没有单独执行该用例。

### 9.7 copyin、64 字节内核缓冲区与串口输出怎样连接

通过整段范围检查后，sys_write 使用：

```c
uint8 buffer[64];
```

这是一块在内核陷入栈上的临时缓冲区，用来装从用户内存复制来的字节。它与以后 UART 输入的环形缓冲区不是同一结构；数字恰好都可能为 64，职责不同。

每次最多复制 64 字节，再逐个调用 uartputc_sync 输出，随后继续下一段。例如请求 70 字节，循环应处理 64 和 6 两段；这是说明分段算法的例子，本步真实输出用例分别为 3 字节，尚未独立验收大于 64 字节的输出。

这样不必在内核栈上放一个与用户 n 同样大的数组。copyin 也按页内剩余量分段，支持当前格式下逐页读取；跨页既可能有效也可能无效，由每页权限决定，不是“只要跨页就拒绝”。本次映射没有连续两页的用户数据区，因此验证的是跨入无效页的拒绝路径，没有验证跨两张有效数据页的成功路径。

`uartputc_sync` 是 Lab1 已有的同步串口发送函数。**同步**在这里表示调用过程中等待发送寄存器可用并提交字节，当前没有实现异步输出队列；内核这一轮正常请求会一直在原任务的处理路径里执行。

### 9.8 为什么用户文字没有附加 Banner 的点号

Lab1 本人的协议要求打印的每个字节后跟一个点，原 putchar 负责这个格式。例如 Banner 中 H、i 会发成 H.i.。这是实验 1 既定输出协议，不是任意用户 write 数据的一部分。

sys_write 直接调用 uartputc_sync，按原样发送用户请求的字节。否则 `write(1, "Hi\n", 3)` 若多插点号，终端收到的就不是那三个用户字节。

因此本步的串口输出由两部分组成：

```text
前 446 字节：原 Lab1 输出，仍按 expect_banner.txt 逐字节匹配。
新增 6 字节：H i 换行 O K 换行，来自用户 write，按原样匹配。
```

测试用 stdout 输出栈里的 Hi，用 stderr 输出代码页内只读字符串 OK，说明 fd=1/2 均可用，也说明输入源页只需要用户可读。标准错误目前不会显示到另外一扇窗口，两种目标都连到相同串口。

## 第 10 步：exit 结束用户任务，记录退出码并留在内核

### 10.1 为什么 exit 不能像 getpid 一样返回用户

getpid 是“告诉我身份”，write 是“帮我输出数据”，请求完成后用户还要继续做事。exit 则是“我不再继续运行，请结束当前任务”。如果内核处理 exit 后仍恢复用户执行，便违背了这次请求的含义。

先看一个用户 C 示例：

```c
write(1, "done\n", 5);
exit(0);
write(1, "wrong\n", 6); // 正确退出时，这行不会执行。
```

这里的代码用于解释语义；本步实际汇编测试会在 exit 后写 FAIL 标记，确认后面的代码没有执行。我们暂时没有完整进程调度，因此选择结束唯一用户任务后留在安全的内核等待循环，而不是切换到另一份用户程序。

### 10.2 exit(0)、exit(7)、exit(-3) 分别表示什么

**退出码（exit status）**是程序结束时交给操作系统的一项结果。通常约定 0 表示成功，非零表示程序定义的失败或其他结束原因；具体每个非零数字意味着什么，由程序约定，并不是 CPU 的异常原因表。

| 调用 | 表示的事情 | 本步保存结果 |
|---|---|---|
| `exit(0)` | 程序按约定报告成功并结束 | 0 |
| `exit(7)` | 程序报告状态 7 并结束 | 7 |
| `exit(-3)` | 程序提供一个负的 int 状态并结束 | -3 的有符号含义 |

例如一个检查输入的程序可以自行约定“7 表示输入格式不对”。这个例子不是说操作系统统一规定 7 就是格式错误。也不要把 exit(7) 与 exec 调用号 7 混淆：exit 的调用号始终是 2，参数 7 只是该请求携带的数据。

本步三种状态都有真实测试。负数用例用于确认 int 参数的解释，不代表已实现完整 Unix wait 状态编码。以后 wait 怎样把结果交给父进程，需要按我们的课程接口另外实现。

### 10.3 普通函数 return 为什么不等同于结束进程

**函数调用**是在当前程序内部转去运行一段代码，通常记录一个返回地址；**return** 是结束这次函数调用，回到调用者。例如：

```c
int twice(int x)
{
  return x * 2;
}

int value = twice(3); // value 得到 6，程序继续运行。
```

这个 return 不改变当前任务的 PID，也不将任务标记为结束。exit 则通过系统调用让内核改变任务状态，成功后不会再回到原用户调用者。

在有完整运行库的普通系统里，main 返回后，启动代码可能再调用 exit。这是启动代码帮忙完成的行为，不是 CPU 看见 main 的 return 就自动销毁进程。当前最小汇编测试没有这样的运行库，所以必须明确请求 exit，不能随意 ret 到一个没有准备好的地址。

赠送 user.h 将 exit 声明成 noreturn。**noreturn** 告诉编译器“这个调用成功后不会按普通函数方式返回”，有助于生成控制流；它本身不是结束进程的硬件指令，也不代替内核实现。

### 10.4 exit 的调用号、参数和分发路径

赠送 syscall.h 规定 SYS_exit=2，本步没有修改编号。用户发出 exit(7) 时：

```text
a7 = 2       选择 exit 服务
a0 = 7       提交退出码
ecall        真正进入内核
```

跳板仍保存 31 个普通寄存器、切到内核栈和页表，然后由 trap.c 保存 sepc 并识别用户 ecall。syscall.c 新增：

```c
case SYS_exit:
  proc_exit((int)(uint32)argraw(tf, 0));
```

argraw 从现场读取第一个参数。课程接口规定 exit 接收 int，所以取低 32 位并按目标 RISC-V GCC 的有符号 int 解释。对 exit(-3)，低 32 位为 0xfffffffd，按补码解释为 -3；保存进 64 位槽时进行符号扩展，得到 0xfffffffffffffffd。

**符号扩展**是将负的较窄整数放进较宽整数时，用原符号位填充高位，使它的有符号数值不变。这里退出记录采用 uint64 存储位模式，测试工具按预期位模式比较，讲解则用有符号的 -3 表示其含义。

proc_exit 被声明为 noreturn，所以该分支不需要先 return 一个普通结果。因为它不会返回到 syscall_dispatch，trap.c 中 `tf->a0 = syscall_dispatch(tf)` 的赋值也不会完成；现场 a0 仍记录用户原来的退出参数。**退出码是请求参数，不是 exit 返回给已结束程序的返回值。**

### 10.5 任务状态怎样记录，为什么还保留那条记录

本步在 proc 中增加 state 和 exit_status。状态用命名常量表示：

```c
enum proc_state { PROC_UNUSED = 0, PROC_RUNNING = 1, PROC_EXITED = 2 };
```

**enum（枚举）**给一组整数起名字，方便表达含义。这里 2 在 state 字段里表示已退出，在 a7 里则表示 exit 调用号；它们出现于不同位置，不能互换解释。

启动时 proc_boot_init 设置 PID=1、state=RUNNING、exit_status=0。程序发出 exit 后：

```c
intr_off();
struct proc *p = myproc();
p->exit_status = (uint64)(long)status;
p->state = PROC_EXITED;
proc_exit_idle();
```

可以用状态表跟踪 exit(7)：

| 时刻 | pid | state | exit_status |
|---|---|---|---|
| 用户启动 | 1 | RUNNING | 0，占位值 |
| 用户运行 getpid/write | 1 | RUNNING | 0，尚未退出 |
| 内核完成 exit 记录 | 1 | EXITED | 7，真实退出结果 |

state 表示该记录目前处于哪个阶段，不能只看到 exit_status=0 就认定程序已成功结束：运行时占位也可能为 0。因此检查同时核对 state 和结果。

当前没有父进程、wait、资源分配器和回收流程，所以先保留 PID、页表指针及结果，便于验收。记录保留不表示用户继续运行。完整进程管理以后会涉及关闭资源、释放内存、通知父进程，以及由 wait 收集结果；这些尚未在本步实现。当前 EXITED 是我们自己的简化状态，不是已经完成 xv6 全套僵尸进程管理。

### 10.6 CPU 为什么还能运行，退出的是谁

用户任务结束，不等于操作系统结束，也不等于 QEMU 关闭。内核仍在执行自己的指令，只是不再恢复这份用户现场。

本步在自有 kernel_trap_entry.S 中增加独立等待入口：

```asm
proc_exit_idle:
    wfi
    j proc_exit_idle
```

proc_exit 在 S 态调用它，当前仍使用内核页表和内核陷入栈，stvec 指向内核入口，tp 保存 hart 0。当前中断关闭，尚未接设备处理链路，因此不会因为本步加了 wfi 就能接受键盘。

**wfi（Wait For Interrupt）**表示等待中断的一类处理器提示。是否暂停、何时恢复受实现和中断条件影响；代码不能假设它永远不返回，所以后面仍有跳回自身的指令。这里等待循环的保证是“即使 wfi 结束，也继续内核循环”，并不依赖它一定物理睡眠。

将来有调度器时，结束一个任务后可以选择下一个可运行任务；当前只有唯一启动任务，选择内核等待是本阶段的过渡方案。不能把这段等待当成已经实现调度，也不能把它叫作 CPU 硬件关机。

### 10.7 为什么 sepc 还是退出指令，现场 epc 却已经加了 4

本次用户 exit 的实际 ecall 地址为 0x119c。trap.c 的通用 ecall 处理先保存这个位置，再将现场 epc 加 4，因此现场 epc=0x11a0。

| 数据或位置 | exit 请求后的值 | 用途 |
|---|---|---|
| 硬件 sepc | 0x119c | 硬件记录的退出 ecall 位置 |
| 内存 tf->epc | 0x11a0 | 通用 ecall 处理计算的下一条位置 |
| CPU 当前 PC | 内核 proc_exit_idle 内 | 现在真正执行的等待指令 |

getpid/write 会走 prepare_return，将现场 epc 写回硬件 sepc 并 sret。exit 不返回到分发调用者，也不走 prepare_return，所以硬件 sepc 没有改成 0x11a0，现场的这个下一条地址也不会被用来恢复用户。

这说明“内存里存着某个地址”与“CPU 将执行那个地址”是不同事情。真正执行目标取决于控制流是否到达相应的返回指令；本次没有执行 exit 后的 sret。

### 10.8 怎样证明退出后的用户代码没有偷偷继续运行

测试先完成原 getpid/write 与寄存器检查，写 PASS 标记到用户栈，然后执行 exit(7)。在 exit 之后故意放置：

```asm
user_probe_exit:
    ecall
user_probe_after_exit:
    li t0, 0x3ff8
    li t1, 0x4641494c   # FAIL 标记
    sd t1, 0(t0)
```

如果 exit 被当作普通服务返回，这条存储就会把 PASS 改成 FAIL。工具既检查标记未改变，也检查任务记录为 EXITED、退出码正确，并确认当前 PC 在内核等待入口、satp 为内核值、sp 在内核陷入栈中、tp=0、stvec 为内核入口。多项证据结合，避免把“用户写过 PASS”误当作“后来已经正确退出”。

真实硬件日志还必须恰好有 14 次用户 ecall：之前 13 次服务请求加最后的 exit，没有多余异常或退出后的额外请求。

正式测试程序默认退出码为 7。新增 check_exit.py 先检查正式内核，再在临时目录只重新编译自有用户测试，分别设置退出码为 0 和 -3，链接两份独立测试内核。不会覆盖正式 kernel/kernel，也不修改赠送用户程序。

### 10.10 本步结论与下一小步

PDF 阶段二的 getpid/write/exit 基础服务已在自有真实用户测试中接通。赠送 hi、badecall 等用户程序尚未装载执行，最终课程程序验收仍要后续补做；多进程、父子关系、wait 回收、键盘输入和 Shell 尚未完成。

验收可以这样回答：“exit 的调用号是 2，a0 是有符号退出状态。分发器调用不返回的 proc_exit，记录状态后停留在内核等待入口，不恢复用户执行。exit(0/7/-3) 都有真实测试；exit 后的 FAIL 指令没有执行，CPU 使用内核页表、内核栈和内核入口。当前只管理一个任务，资源回收和调度后续完善。”

接下来转入 PDF 阶段三。先准备能保存现场并安全返回的内核中断入口，再逐步接 UART、PLIC 和输入缓冲。原因是当前 kernel_trap_entry 只会诊断停机；若先开启正常中断，内核无法处理完继续执行。等你说“下一步”再继续。

## 第 11 步：内核中断入口保存现场，处理后安全返回

### 11.1 用户能陷入返回，为什么还需要内核自己的返回入口

用户程序运行时，stvec 指向跳板 uservec；用户请求进入内核后，stvec 切到 kernel_trap_entry。前一步的内核入口遇到任何事件都诊断停机，这适合排查错误，却不能用于正常设备中断。

PDF 阶段三要接键盘输入：串口收到字符时，中断可能发生在用户运行期间，也可能发生在内核正在处理别的请求时。因此先让**内核自己的执行现场**能够保存、处理和恢复。

例如内核正在完成一次 write，串口恰好又收到一个字符。最终应能暂时处理接收事件，再回来继续原输出，而不是每次接收都让内核停机。本步先构造保存返回通道，用真实软件中断验证；UART 接收事件下一小步再接上。

### 11.2 一个寄存器被打断的例子：t0=40 怎样才能继续算出 41

假设内核汇编正准备执行：

```asm
# t0 当前为 40
addi t0, t0, 1    # 原本应得到 41
```

执行这条加法前发生中断，处理函数可能把 t0 用来临时放某个设备地址。若返回时不恢复 t0，加法就会拿设备地址加 1，而不是 40 加 1，原计算被悄悄破坏。

正确过程应是：

```text
保存 t0=40 → 中断处理自由使用临时寄存器
→ 恢复 t0=40 → 执行原加法 → 得到 41
```

**中断**可以在正常执行过程中的指令边界出现，被打断的代码没有主动按普通函数调用规则交出寄存器。虽然 C 函数调用约定要求保存某些寄存器，但 a0/a1/t0 等通常允许被被调函数改写；异步中断不能因此丢掉它们。入口必须替原执行流程保存需要恢复的全部普通整数寄存器。

本步保存 x1 到 x31 共 31 个整数寄存器。x0 永远为 0，无需保存。这里不包括浮点或向量寄存器；当前内核处理路径没有启用它们的上下文管理。

### 11.3 用户陷入与内核陷入使用不同的现场位置

| 比较项 | 用户进入内核 | 内核执行时发生陷入 |
|---|---|---|
| 硬件切入处理入口后的权限 | S 态 | 仍是 S 态 |
| 最开始的 sp | 用户给出的栈位置 | 已有的内核栈位置 |
| 保存寄存器的位置 | 高地址 TRAPFRAME 对应的现场页 | 当前内核栈上新留出的空间 |
| 是否需要切到内核页表 | 需要，由跳板完成 | 不需要，已经使用内核页表 |
| 正常结束后去哪里 | 根据准备状态返回 U 态 | 恢复原来的 S 态执行位置 |

例如用户现场中保存着用户 sp=0x4000，内核当前 sp 位于 0x8000b000 一带。若内核中断沿用 uservec 保存位置，会把用户的 sp 等字段覆盖成内核值。以后返回用户时恢复的就不再是正确用户现场。

因此新增入口只在自己的内核栈上保存数据，不访问 TRAPFRAME。测试会事先给用户现场的全部 288 字节填入可识别数据，再检查内核中断后完全不变。

这里也不需要跳到高地址 TRAMPOLINE 切页表，因为本来就没有换页表的需求；kernel_trap_entry 是内核页表能执行的正常代码入口。

### 11.4 为什么留 256 字节，栈上每一项怎样放

入口首先执行：

```asm
addi sp, sp, -256
```

31 项乘 8 字节为 248 字节。RISC-V C 调用约定要求栈指针保持 16 字节对齐，所以向上留到 256 字节，最后 8 字节为对齐空位。这块空间可称为本次陷入的**栈帧（stack frame）**，表示为这次处理在栈上保留的一段存储。

部分布局如下，偏移以减小后的 sp 为起点：

| 偏移 | 内容 |
|---|---|
| 0 | 原 ra |
| 8 | 减小前的原 sp |
| 16 / 24 | 原 gp / tp |
| 32 / 40 / 48 | 原 t0 / t1 / t2 |
| 72 | 原 a0 |
| 128 | 原 a7 |
| 240 | 原 t6 |
| 248～255 | 对齐空位 |

这是自有内核入口的栈布局，不能把它的偏移套到赠送用户 trapframe 上。例如用户 a0 位于偏移 112，本步内核栈帧 a0 位于偏移 72，两者存储起点和前置字段不同。

用具体地址算一次：原 sp=0x8000bff0，减 256 后为 0x8000bef0，新保存范围是 `[0x8000bef0,0x8000bff0)`。原 sp 仍需要记住，以便恢复成 0x8000bff0，而不是误留在 0x8000bef0。

调用 C 处理函数时，C 函数还可以继续向低地址使用自己的栈空间；保存区位于调用时 sp 的上方，正常调用规则不会把它当作 C 函数的局部空间随意覆盖。

### 11.5 保存 sp 的小问题：怎样算原值，又不丢掉 t0

减小 sp 后，不能直接 `sd sp,8(sp)` 作为原栈指针，因为那样保存的是减小后的地址。入口先保存 t0 原值，然后借它计算：

```asm
sd t0, 32(sp)       # 先记住被打断时的 t0
addi t0, sp, 256    # 新 sp 加 256，得到原 sp
sd t0, 8(sp)        # 保存原栈指针
call kerneltrap
```

这个顺序与用户跳板借 sscratch 保存 a0 的道理类似：需要一个临时寄存器做工作，就必须先保护它原来的内容。这里已经有可信的内核栈，所以不需要借用户现场页解决。

call 会改变 ra，C 处理也可能改变其他普通寄存器。入口已经把 ra 等全部保存，返回后逐项 ld 恢复，最后才执行：

```asm
ld sp, 8(sp)
sret
```

sp 必须最后恢复。若先把它改回原位置，后面的 `ld a0,72(sp)` 等将从错误的基址读取。先恢复其余寄存器，再用保存的 sp 回到原栈位置，随后交给 sret 进行陷入返回。

### 11.6 C 的 kerneltrap 检查什么，为什么不能把所有事件都忽略

新增 kerneltrap 先读取 sepc、sstatus、scause。来自 S 态的陷入应当有 SPP=1，且硬件进入处理时应已经清 SIE。若这两个条件不符，诊断并停止，避免按错误来源恢复状态。

本步只接通监督级软件中断：

```c
if (cause == ((1UL << 63) | 1)) {
  w_sip(r_sip() & ~2UL);
  kernel_softirq_count++;
} else {
  kerneltrap_stop();
}
w_sepc(epc);
w_sstatus(status);
```

最高位 1 表示中断，低原因号 1 表示监督级软件中断。其他异常和尚未接通的外部中断仍诊断停机。本步没有以“能返回”为理由跳过真实错误；非法指令通常意味着内核代码本身不正确，不应随意忽略后继续。

kernel_softirq_count 记录处理次数。它使用 volatile，要求编译器保留实际的内存读写，方便观察；volatile 不是锁或多核原子操作，本步只有 hart 0 且处理期间不重新开中断。

### 11.7 软件请求位、类别开关和总开关，各自管什么

**监督级软件中断**是软件设置请求位，再由 CPU 按硬件中断规则响应的事件。它不是直接调用 C 函数，也不是向 scause 手工写一个值冒充已经陷入。

| 名称 | 本步相关位 | 作用 |
|---|---|---|
| sip | SSIP，位 1，数值掩码 2 | 是否有待处理的软件请求 |
| sie | SSIE，位 1，数值掩码 2 | 是否允许这种类别进入 S 态处理 |
| sstatus | SIE，位 1，数值掩码 2 | 当前在 S 态时的中断总开关 |

三者掩码碰巧都为 2，但处在不同寄存器中，作用不一样。可以类比“有人按门铃”“允许接收这种门铃”“现在允许接待”三项条件，单独只满足一项并不代表处理已经发生。启动代码还需要把此类事件委托给 S 态，这项前期已配置。

临时测试先写 sie=2、设置 sip.SSIP，然后给所有测试寄存器准备值，最后才置 sstatus.SIE。请求早已待处理，但总开关没开时不打断初始化；开关打开后，CPU 真正记录 scause/sepc 并跳进内核入口。

处理时清 SSIP 是**确认并消除当前请求**。如果不清，sret 恢复开关后会再次响应同一个请求，原代码难以继续。类别开关仍可保留，使以后新的请求能进入。下一步 UART/PLIC 的确认方式不同，需要读取设备和完成中断，不能机械照搬清 SSIP 的语句。

正式用户启动流程没有新增这些使能操作，软件中断仅在独立测试内核中触发；本步不会让尚未实现的 UART 处理收到正常键盘中断。

### 11.8 为什么中断不把 sepc 加 4，SPP 又该怎样恢复

用户 ecall 是主动执行的一条请求指令，正常处理后应跳过它。中断是插入原执行过程的事件，sepc 指向应该恢复执行的位置，内核不能无条件跳过一条原指令。

用第一节的加法例子：中断返回位置正是 `addi t0,t0,1`。若把地址加 4，可能跳过加法，结果仍为 40；而且本项目也支持 2 字节压缩指令，不能认为任意“下一条”都相距 4。本步 kerneltrap 保存并写回原 sepc，不推进它。

返回到内核时，要保留 SPP=1，sret 据此选择 S 态；不能照抄用户返回时清 SPP 的做法，否则会错误降到 U 态执行内核地址。

```text
S 态正常运行，SIE=1
→ 硬件中断：SPP=1，原 SIE 保存到 SPIE，当前 SIE=0
→ C 处理，写回保存的 sepc/sstatus
→ sret：返回 S 态，把 SPIE 恢复到 SIE
```

sret 执行后 SPP 会被硬件清零，这并不表示当前已经在 U 态：它是“之前权限/下一次返回选择”的状态字段，不是直接读取当前权限的标签。返回的实际权限由执行 sret 时的 SPP 决定。

当前处理中保持 SIE=0，不实现主动开启的嵌套中断。保存 CSR 让 C 处理与返回协议清楚，但不能由此宣称复杂嵌套或调度切换已经通过。

### 11.9 真实测试怎样证明寄存器与用户现场都没有丢

新增 check_kernel_irq.py 在临时目录链接两份独立测试内核，正式 kernel/kernel 不被覆盖。正常用例先把用户现场 36 个字段填成 0x9000、0x9001 等识别值，再切到专用、对齐的内核测试栈。

寄存器赋 0x201 到 0x21f 的不同值，sp 使用真实测试栈顶。最后开中断，硬件响应一次已挂起的 SSIP。恢复后的第一批指令立即把 31 个寄存器存到测试栈，使用过临时寄存器后再写完成标记。工具比较快照，确认原 sp、原 sepc、内核 satp 和所有 288 字节用户现场均符合预期。

工具还要求处理次数恰好为 1、SSIP 已清除、硬件日志只有一次 s_software。若返回地址误加 4，恢复位置的第一条存储会被跳过，快照检查也能发现错误。

第二份用例在 S 态真正执行非法指令。新入口仍应保存现场并进入诊断，打印 scause=2、出错 sepc 和 stval=0 后停止，不假装成功返回。此前内核错误入口仅有代码，本步补上了这条真实故障证据。
