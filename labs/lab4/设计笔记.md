## 二、swtch 与两种现场

`swtch(old,new)`的参数分别在 `a0/a1`。保存及恢复 `ra/sp/s0..s11`，偏移0至104，总112字节；proc.h逐项静态断言。`ra`由call写成调用结束后的下一条指令地址，恢复后ret便从该位置继续，因此不另存PC。

严格按[RISC-V psABI整数寄存器约定](https://riscv-non-isa.github.io/riscv-elf-psabi-doc/#_integer_register_convention)，ra属于caller-saved；sp和12个s寄存器需要保持。swtch保存的是“12个s寄存器＋sp＋用于继续执行的ra”，不能把14个统称callee-saved。

其他caller-saved寄存器由C调用约定约束：编译器负责保存跨函数调用仍活跃的值。trapframe处理任意用户指令处的陷入，必须保存31个通用寄存器；context处理正常C调用点的内核执行流切换，保存上述14个即满足本切换协议。多保存寄存器可以另行设计，但增加访存、存储和协议复杂度。

新进程由 `allocate_process`设置 `context.ra=forkret`、`context.sp=私有内核栈顶`。第一次调度进入forkret，先释放p锁，再返回用户态。

## 三、调度器栈与状态机

启动栈保留给 `main → proc_shell_launch → scheduler`，每个进程拥有单独一页内核栈。A退出时仍在A栈上，所以exit只成为ZOMBIE并切走，父亲wait以后释放A栈；调度器不能借用A栈继续执行。

```text
A用户栈 → uservec → A内核栈
         → swtch → 调度器启动栈
         → swtch → B内核栈
         → userret → B用户栈
```

状态图及每个箭头的函数和锁见[完整讲解的状态迁移图](Lab4完整调用图与操作系统作用讲解.md#59-进程状态迁移图)。申请时为USED，完成装载/复制才发布RUNNABLE；调度为RUNNING；yield回RUNNABLE；sleep为SLEEPING；wakeup/kill使睡眠者就绪；exit成为ZOMBIE；wait回收为UNUSED。

## 四、锁保护粒度与顺序

- `p->lock`保护进程状态、chan、killed、策略字段、统计及跨swtch的栈交接。
- `wait_lock`保护父子关系及wait扫描/exit通知之间的条件协议，获取顺序为 `wait_lock → p->lock`。
- `tickslock`保护全局ticks及pause的条件判断，调用sleep时交接为当前p锁。
- `input.lock`保护控制台环形缓冲及空读条件，调用sleep时交接为当前p锁。
- `pid_lock`只保护pid分配，不带它进入sched。

调度器切入持p锁，恢复的进程在sched返回后释放；进程切出持p锁，恢复的调度器释放。新进程经forkret承担第一次释放。四条断言是持自身锁、noff等于1、状态不是RUNNING、中断关闭。sched保存并恢复intena，避免其他进程改变CPU字段影响当前执行流。

无独立就绪队列锁；本单核实现关中断扫描进程表，逐个取p锁读取候选，最后拿获胜者的锁切入。该选择方式不作为双核安全实现的证据。

## 五、丢失唤醒推演

错误交错：A持条件锁发现无资源，释放条件锁；B生产资源，wakeup时A还不是SLEEPING；A随后登记SLEEPING并切走。若事件只发生一次，A可能永远睡眠。

正确sleep顺序：持lk检查条件 → 获取p锁 → 释放lk → 设置chan/SLEEPING → sched。生产者修改条件后需要通过wakeup获取A锁，无法越过A登记休眠的过程。A恢复后先清chan并放p锁，再重新获取lk重查条件。

wait/exit共同使用wait_lock，使父亲扫描孩子、决定睡眠与孩子发布ZOMBIE和通知构成同一条件协议。唤醒可以早于状态写入，但父亲必须等exit释放wait_lock以后才可重查。

已使用 [check_lab4_lost_wakeup.py](../../tools/check_lab4_lost_wakeup.py)在临时目录生成故障源码与镜像，改为先释放lk、空转一百万次、再获取p锁；对wait条件在窗口中插入yield，控制孩子先运行并退出。只在用户态抢占的单核内核中，单纯内核空转不足以强制孩子获得CPU，所以必须说明这一步交错控制。

[lost-wakeup.txt](evidence/lost-wakeup.txt)记录错误版本已到达窗口，bench首轮fork/wait阻塞，未产生第一行平均耗时。正式源码和镜像从未替换，正式bench完成100轮及8孩子回收。有限日志观察与交错推演共同说明该缺陷，不把推演冒充运行结果。

## 六、ID9策略选择

两级0/1，1优先。初始shell基本级别为1，fork继承父亲基本优先级和票数，统计为0，临时提升不继承。exec替换镜像但保留进程身份、策略和累计统计。

`setpriority(0/1)`使用本地26号，返回旧基本优先级，非法值-1。课程 `setickets(n>=1)`仍记录并返回0，初始为17，在ID9中不用于选择。

每次全局tick扫描低级RUNNABLE进程，ready_ticks到8即将有效优先级提升为1。只计准备好运行却没被选中的时间，不把等待I/O的SLEEPING时长作为CPU饥饿。调度选中后有效级别回base，这次提升已经带来一次运行机会；低级再次就绪后重新累计。

同级通过rr_idx环形起点轮转，比较时只有严格更高优先级才替换候选，避免固定低槽位独占。

## 七、时钟与统计口径

`stimecmp=time+100000`，QEMU virt下标称10ms一拍；一个tick是一次时钟中断，LAB2_TICK=2表示两个用户态时钟采样构成一个片。全局ticks在内核与用户时钟中均增加，cpu_ticks/slice只在usertrap时钟分支增加。

scheduler每次分发清零slice；用户分支先计数再判断是否yield；内核时钟只推进全局时间、唤醒和老化。kerneltrap保存及恢复sepc/sstatus；本实现不在内核时钟中抢占。
